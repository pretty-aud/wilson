## F5 — One roster, one rate card, one project load

**Nothing new on the screen.** F5 changed how often the app asks the server
for things it already has. Every page looks and behaves as before; it just
asks less, and what one page changes the others see at once.

**What changed, in plain words.**

1. **The company's people list is read once.** Before, every page and
   picker that shows people (the Dashboard, Team Members, the Rate Card page,
   R.A.B.B.I.T., the Admin terminal, Scenes, the Timeline) asked the server
   for the whole list itself, some of them twice. Now the app asks once and
   every page reads that one copy. When someone in the company is changed
   (renamed, deactivated, invited), every page sees it, not only the two
   that used to listen.
2. **A project opens with one load instead of two.** Opening a project
   loaded it, then loaded it again as soon as the live connection came up.
   Now the app waits for the live connection (at most half a second) and
   loads once. A change another person makes while the project is loading
   is no longer lost. Opening a project also no longer reads the comments of
   every other project in the company.
3. **The rate card is read once.** Nine places that show rates each read
   the cards, the rates and the department defaults themselves. Now they
   share one copy, and an edit on the Rate Card page shows everywhere at
   once. A place you open later still reads the rates fresh (once, for all
   of them), so it never shows rates the server has since changed.
4. **Who is on a project is read once.** Opening a project read its team
   twice, and the two copies drifted: adding someone to a project showed in
   one place and not in Budget or the Timeline until the next reload. Now
   there is one copy.
5. **Big projects are read whole.** A project with more than 1,000 of one
   kind of thing (phases, levels, experiences, milestones, folders, assets,
   tasks, scenes, shots) lost the ones past 1,000 in some views and in
   D.O.G.'s references. Every list is now read page by page.
6. **New shots and file drops ask less.** A new shot read the whole folder
   tree twice; now once. A drop of ten files looked up the same folder and
   scene ten times each; now once per drop. Whether the project is private
   is still checked for every file, on purpose: that check decides where a
   private project's files are kept.
7. **Who is signed in is held once.** Thirty-eight places each kept their
   own copy of who is signed in, asked for it at launch and redrew every
   time the sign-in was quietly renewed. Now there is one copy, and a
   renewal that changes nothing redraws nothing. The app also takes your
   company from the sign-in itself everywhere, as the server does, so the
   live connection, the error log and the model choices can no longer point
   at a company you were removed from.

**How it was checked.** Each change has a test that counts the server calls
against a stand-in server, run first on the old code (where it failed with
the old count) and then on the new code. The numbers, before and after:

| What was counted | Before | After |
|---|---|---|
| People-list calls for seven readers | 10 | 1 |
| ...after one change to a person | reached 0 of 7 readers | 1 more call, all 7 see it |
| People-list calls at an admin's launch (from the pages mounted) | 8 | 2 (the first read, and one when the live connection joins) |
| Full project loads per open | 2 | 1 |
| A change sent while the project loads | lost | kept |
| Comments from another project read on open | all of them | none |
| Rate card reads for nine readers (cards, rates, defaults) | 1, 9, 9 | 1, 1, 1 |
| A rate edit seen by the other readers | 0 of 8 | 8 of 8 |
| Project team reads per open | 2 | 1 |
| Rows read of a kind with 1,001 in the project | 1,000 | 1,001 |
| Folder-tree reads for one New shot | 2 | 1 |
| Repeated lookups for a drop of ten files on a shot | 30 | 12 (the privacy check stays per file) |
| Sign-in listeners and reads for 37 permission readers | 37 and 37 | 1 and 1 |
| Readers redrawn by a quiet sign-in renewal | all 37 | none |
| A sign-in whose company differs from the account record | the account record's company | the sign-in's |

**What to look at, if you want to.** Nothing needs checking: everything above
is counted by tests. If you like, open a project, add someone to it on its
team, and see them on Budget and the Timeline without reloading; or edit a
rate on the Rate Card page and see it in a project's Budget at once.

## F6 — D.O.G. and O.T.T.E.R. without their copies

**Almost nothing new on the screen.** D.O.G. and O.T.T.E.R. each did some
jobs in two or three places, with copies that had drifted apart. F6 left one
copy of each. Decks, courses and lessons come out as before; a few failures
now say why, and three small differences in generated subjects are fixed.

**What changed, in plain words.**

1. **The Validator asks the AI the way the rest of O.T.T.E.R. does.** It
   had its own way of calling the AI, which kept the AI's first sentence
   ("Let me check the manual…") instead of its answer, gave up when a web
   search paused, and never retried when the AI service was busy. It now
   uses O.T.T.E.R.'s one way: it waits out a paused search (at most three
   times), retries a busy service after 3, 6 and 12 seconds, and reads the
   answer, not the preamble. What it sends is unchanged.
2. **O.T.T.E.R. reads every server answer one way.** When the server said
   no with a page that was not data, up to 82 places could show
   "Unexpected token '<'" instead of their own sentence, and some kept a refusal as if it were a
   course, a subject or your hotkeys. Now each shows its own words. Export
   says why it failed instead of saving the error as the export file, and a
   course that cannot be read opens empty instead of showing the previous
   course under its name.
3. **D.O.G. reads its slide format in one place.** Generating a deck,
   bringing one in through History and drawing a slide each had their own
   copy of how a slide is read. Generating and drawing now share one
   reading, and generating and bringing in share one frame. Where generating and
   bringing in still read the same text differently, nothing was changed
   (that would change a deck); the six cases are written down
   (OUTSTANDING F6-01 to F6-06).
4. **D.O.G.'s Rewrite and its Regenerate send one request**, written once
   instead of twice.
5. **O.T.T.E.R.'s five ways of generating** (a course outline from the New
   course screen, a single subject, filling an outline subject, and the pet
   agent's course and subject) share one set of steps. Three differences
   between the copies are gone: a key takeaway the AI sends as one sentence
   is kept everywhere (two paths dropped it), the agent's hint about node
   types is complete again, and the agent's "too long" sentence is the
   course screen's. The "share new subjects?" reminder stays on every path
   that saves.
6. **D.O.G.'s prompt boxes now work.** You chose "Make them work". The two
   Generation Rules boxes and the Single Page and Full Deck Export Schema
   boxes are now what D.O.G. sends for a new slide or a new deck. They start
   from exactly the words it sent before, so no deck changes until you edit
   one; an edit is used from the next generation until you press Reset or
   WILSON restarts. Where the rules box says {{EXPORT SCHEMA}}, the schema is
   put in. Regenerating a page still uses D.O.G.'s built-in rules. The Image
   Prompt Export Schema shows the layout of the file D.O.G. writes itself,
   so it is now read-only, like the Visual Deck one beside it.

**Before and after, measured.**

| | Before | After |
|---|---|---|
| Direct server reads that could show "Unexpected token" | 83 | 1 (the pet's own, already safe) |
| Lines in O.T.T.E.R.'s five generators | 1,028 | 443, plus one shared pipeline |
| Copies of the rule that turns a course or subject name into its id | 8 | 0 (one shared rule) |
| D.O.G.'s generation splitter / History import splitter (lines) | 173 / 89 | 9 / 16, plus one shared reader |
| D.O.G.'s Rewrite and Regenerate (lines) | 148 | 39, plus one shared request |
| The app's main file (bytes) | 5,133,340 | 5,118,113 |

**What was checked.** Each change was first run side by side with the code
it replaced, on the same inputs, and compared: the slide splitter on 14 real
and awkward deck texts, the rewrite on 49 selections for both buttons, and
the generators on 12 courses and subjects (every request to the AI, every
save, every share reminder). They matched, apart from the three fixes
above. Five reviewers then read the work; one also ran about 600,000
comparisons of its own and found no difference in D.O.G. They found three
mistakes of F6's own, fixed the same morning: a leftover from a check that
skipped subjects named "General Basic…", a change that broke a measuring
script, and the course-opens-empty case above. Everything else they found
is written down (OUTSTANDING F6-07 to F6-34).

**Nothing to test by hand is required.** If you want to look: generate a
subject in O.T.T.E.R. and validate a lesson; in D.O.G., rewrite a sentence
and press Regenerate, and bring a deck in through History. All should
behave as they did.

## F9 — The desktop's twins

**One thing you can see: thumbnails in a demo folder show again.** The rest
is inside the desktop app. Several jobs were written several times there, and
the copies had drifted apart; F9 left one of each. Nothing else on the screen
changes.

**What changed, in plain words.**

1. **Pictures in a demo folder.** While a demo folder was open, every
   thumbnail WILSON had already made — an asset's, a scene's, a shot's, a
   managed file's, a bin clip's — failed to load (the desktop answered
   "internal error"), because it lives in the folder's hidden `.wilson`
   folder. They load now.
2. **Every file the desktop sends goes out one way.** A file's bytes left the
   desktop's server from 22 places with different rules. Now one sender does
   it: the browser inside WILSON never keeps a copy of your footage or its
   previews in its cache (most places let it before), every one of them
   answers WILSON's own window and nothing else on your computer, and a video
   still seeks. One small difference: asking for a part of a file past its
   end now says so (416) instead of "failed". A private project's media also
   reads from a demo folder kept inside a hidden folder, which it refused.
3. **"Where is this project's folder?" is answered once.** Two answers in the
   desktop and four in the screens could disagree. Now there is one, so the
   copy into a project folder, Show in folder and Open folder all agree with
   the desktop. Two old dangers are gone with it: a project whose title has
   no Latin letter or digit (東京, 🎬) was given the whole storage folder as
   its own, and deleting an asset with such a name moved every asset's folder
   to the trash. Such a project now gets a folder of its own, `Untitled-Project-`
   and the first eight letters of its id, and such an asset likewise.
4. **Thumbnails are made one way.** Six places made them, and only one was
   careful. Now every thumbnail is written whole before anyone can see it
   (a half-written one used to stay broken for good), two tiles asking for
   the same one make it once, and picking a new picture always wins over one
   still being made.
5. **The desktop's rules are written once.** Task items, saved table views,
   the shot lists' first order, O.T.T.E.R.'s hotkeys and functions merges and
   the bins' media types were kept twice, once for the screens and once for
   the desktop. The desktop's copies are now made from the screens' own
   files by a script, and a test fails if they ever fall behind. The folder
   rules and the list of video types stay twice for now (OUTSTANDING F9-05).

**Before and after, measured.**

| | Before | After |
|---|---|---|
| Places that send a file's bytes | 22 in 6 files | 1 sender (21 sends) and the app's start page |
| Of them, kept out of the window's cache | 2 | 14 (the bins' 7 thumbnails keep the old rule, F9-01) |
| Of them, answering WILSON's window only | 11 | 21 |
| A cached thumbnail in a demo folder | "internal error" | the picture |
| Answers to "where is the project's folder" | 2 in the desktop, 4 in the screens | 1 and 1 |
| Places that make a thumbnail / accept one | 6 / 3 | 1 / 1 |
| Rules kept twice by hand | 714 lines in 5 files | 0 (the folder rules and the video types still twice) |
| The desktop's main file (lines) | 5,908 | 5,548 |
| The app's main file (bytes) | 5,093,158 | 5,092,452 |
| The desktop's own folder (bytes) | 893,992 | 916,487 |

**What was checked.** Each fix was first shown failing on the old code, then
passing: 23 checks of the sender, 7 of the folder answer, 4 of the thumbnails
(kept beside the old code's own words), and 2 of the rule copies' check.
The old eight "do the copies agree" tests ran unchanged on the new copies and
passed before the comparisons they no longer need were removed.

Four reviewers then read the work, one part each. None found a security
hole made by F9. They found mistakes of F9's own, fixed the same evening: a
file whose network drive dropped in the middle left the window waiting for
ever; two projects whose names have no Latin letter would have shared one
folder, so renaming one moved the other's files; a busy virus scan could
pause the whole desktop app for up to a fifth of a second per thumbnail; and
the check of the copied rules had a few blind spots. What they found outside
F9's own work is written down (OUTSTANDING F9-01 to F9-13). One thing will be
yours to decide: a project made before F9 with such a title keeps the whole
storage folder as its own until its files are moved (F9-02).

**Nothing to test by hand is required.** If you want to look: open a demo
folder (Settings → Storage) and open a project's Assets, Scenes and Files —
the thumbnails should show; add a file to an asset; play a video clip and
drag along it; pick a new picture for an asset.
