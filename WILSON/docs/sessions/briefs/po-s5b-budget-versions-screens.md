## Step 0 (new, before step 3): rows that are not part of the open version are SET ASIDE, never lost

Design it first, in writing (a short section in your hand-off, committed before the code), then build it. **Hard constraints — each one gets a test and a planted-fault control:**

1. **Nothing attached to a row is lost by switching versions**: a set-aside task keeps its comments, files and links, dependencies, assignments, logged time, scene and shot links; the same for a phase and a key date. Opening the version that holds it brings back the SAME row (same id), with everything on it.
2. **The trash is not the store.** R.A.B.B.I.T.'s trash is purged after 30 days (0014) and is what "Recently deleted" lists: a set-aside row is neither listed there nor ever purged. (Part 1's `reviveBudgetRow` still serves a row a person really deleted.)
3. **Set aside means hidden everywhere the row would otherwise show or count**: the Timeline, Tasks, Budget (bid days, logged days, variance, every report), the Summary's tiles, dependency and task pickers, the pet's knowledge, exports, any cross-project list. Enumerate every reader of tasks, phases and milestones on all three backends and say in the hand-off which you changed and which never showed them.
4. **Work is never hidden unasked.** If a row about to be set aside has logged time, comments or files on it, the "Edit this version" question says so by count and name and offers to keep those rows in the version being opened (they then count as its unsaved changes) — or to set them aside anyway — or Cancel. Cancel first and focused.
5. **The same on the cloud, the Local Server and the dev fixtures** (A9). The Local Server hard-deletes today: it needs the same set-aside state, not a delete.
6. **Under a lock nothing is set aside or brought back** (nothing opens while a budget is active — part 1's R1-10): the schedule is the locked version's rows plus whatever is made during production.
7. **One undo step** takes an open back exactly: what it set aside returns, what it brought back is set aside again, values restored.
8. **A row in NO saved version** (made since the last save, with no version open, or left by Discard) is never silently set aside for ever: the Save / Discard / Cancel question before the open covers it, and its Discard says plainly what happens to such rows (deleted the ordinary way, recoverable from Recently deleted for 30 days).
9. **Removing a row while a version is open**: if another saved version holds it, the verb is "Remove from this version" (it is set aside and stays in the other version); only a row no other version holds is really deleted. Say which in the confirm, as S3b's Remove / Delete does for shots (`membershipCopy.js` is the model).
10. **Deleting a version** never strands rows: rows only that version held, and now set aside, are named in the delete question (kept as ordinary rows of the open version? deleted the ordinary way?) — decide with the design skills, say it in the question, record it for Audrey.

**The controller's recommendation (not a ruling — prove it against the code or choose better):** a row state, `set_aside_at` (and which open set it aside), on `tasks`, `phases` and `milestones`, written by the open composite; every loader and query that filters `deleted_at IS NULL` also filters it; "unsaved changes" and Save read only rows not set aside. The alternative — no column, a provider-level scope computed from the snapshots (`ctx.tasks` = in scope, `ctx.allTasks` for resolution, as S3a did for scenes) — needs a home for "removed since open" and does not reach queries outside the provider; if you choose it, show how constraints 3, 5 and 9 hold.
