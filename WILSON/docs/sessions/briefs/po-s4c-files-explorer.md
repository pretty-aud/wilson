## The work, in order

### 1. The Table view navigates like an explorer (her item 3)

- The Table shows ONE folder's contents at a time: the folders then the files in it, sorted within that folder (`sortRows` on that folder's children, never on the flattened list). Pressing a folder row (click, or Enter on its row) enters it; **a breadcrumb above the table** shows where you are ("Project › SCENES › Proj-Sc01"), each crumb a button; Backspace / Alt+Left goes up; the Columns view keeps the SAME current-folder state (`selected`), so switching views keeps your place, and the file window's Location crumb (`breadcrumb(node.parent)`) matches.
- The **search box** keeps today's behaviour across the whole tree: while a query is typed the Table shows the matching rows from everywhere with their folder in the path column (`filterFlat` on `flattenTree`); clearing the query returns to the current folder. Say so in the empty state ("No files match … in this project").
- The Table's path column goes away in folder mode (the crumb says it) and comes back for search results; the indent-by-depth code and the long note above `TableView` are replaced by this design — the earlier review's objection (an indent that lied about parentage when sorted) no longer arises, because there is no indent and the parent is the crumb.
- Keyboard: arrows move the row focus, Enter opens a folder or previews a file (E10), Backspace goes up; the kit Table's roving focus as the Scenes tab's tables do it.
- Deep-link: entering the Files tab from "Show in Files" (if any caller passes a folder or file) lands in that file's folder with the file selected; `rabbitNavigate`'s existing subscriber shape.

### 2. Shot folders live inside their scene's folder (her item 2)

Today a shot's folder is `SHOTS/<shot-slug>` under the SHOTS category (`folderPaths.js`, `ensureEntityFolder`, `main.cjs`'s folder-path builder), beside `SCENES/<scene-slug>`. From now on a shot's folder is **`SCENES/<scene-slug>/<shot-slug>`**, its parent the scene's folder row; the SHOTS category is no longer created for a new project. A shot whose `scene_id` is null (the column allows it) keeps `SHOTS/<shot-slug>` so nothing is unrepresentable — say so in the hand-off. The rules: `path` computed by ONE function on both backends (`entityFolderPath` grows a scene argument; the Local Server's copy follows it line for line, with the parity test the folder tests already have); the path-shape CHECK and the unique indexes of 0041 already allow the nested path; the storage key becomes `projects/<id>/SCENES/<scene>/<shot>/<file>` — third segment SCENES, so the money gate, the quota exemption and the thumbnail policies are untouched (prove it with the existing suites: 42, 45, 55/78's probes still pass on a nested key).
- **Moving a shot to another scene** (if the Scenes tab allows it) moves its folder — design it with the same move primitive as the re-filing below, or refuse with a sentence until it exists; say which.
- **Existing projects are RE-FILED, never left half-moved.** A one-time, per-project action for whoever can write the project: "Move shot folders into their scenes" — offered (not forced) in the Files tab when the project still has shot folders under SHOTS, with the count and the names; on the cloud it moves each object (both buckets: `rabbit-files` and `rabbit-thumbnails`) with the Storage API's move, VERIFIES the object exists at its new key, then rewrites `files.storage_path` and the folder rows (`parent_id`, `path`), one shot folder at a time, idempotent and resumable (a second run finds nothing left to move); on the Local Server it moves the directory and rewrites the bundle's managed-file paths the same way; the empty SHOTS category row and folder are removed only once nothing is left under them. A failure part way leaves a project that still works (the rows describe where the files ARE) and says what is left.
