## What Audrey ruled (the shape you build)

- **D1 + D3.** Shot lists are REAL rows, and a scene or shot may belong to MANY lists: membership, not copies. "New list from the current one" links the same rows; a picker (S3b) adds shots from any earlier list. Consequence to write into the hand-off's first paragraph: a shot's name, description, notes, status and thumbnail are shared by every list that contains it; only membership and order are per list.
- **D2, D5.** The Scenes tab (S3b) VIEWS one list (per person, per project) independent of which list is ACTIVE for the project. Scene/shot field edits stay live-saved; "Save" records a version point (a snapshot); "Save as" creates a new list version.
- **D4, D18.** Lists are archived, never deleted; the active list cannot be archived.
- **D6.** An edit is an ordered list of ITEMS referencing shot ids (repeats allowed), in scene order; "new shots" from an edit become real shot rows; no in/out points; a linear chain per list (title + version); edits may exist on any list, active or not.
- **D8.** Managers, members AND reviewers may create and edit shot lists and edits (reviewers are comment-only today — this is a NEW gate). Set active and archive: workspace admin or project manager only.
- **D9.** Tasks get `scene_id` / `shot_id` in the cloud; assets get their scene/shot links in the cloud.
- **D10.** `ctx.scenes` / `ctx.shots` keep meaning "the ACTIVE list's" for every existing consumer (after the backfill they equal today's rows, so nothing visible changes); new selectors expose the rest.
- **D11.** Backfill: every project with scenes gets "Shot list 1 · v1", active, containing every scene and shot in today's order; no edit is created; on both backends and in the fixtures.
- **D14.** A list is `title` + integer `version`, unique per project, shown "Title · v3".
- **D22.** Takes and files attach to the shot row and are therefore visible from every list.
- **A9.** Both backends in this bundle: Supabase (migration + RLS + pgTAP) and the Local Server (bundle keys + routes + read-time migration) and the dev-fixtures adapter, with the same shapes.

## The schema (migration `0084_shot_lists_and_edits.sql`)

Write it in the house style (a header that says what it is, why, the ordering pairs — after 0040 scenes/shots, 0037 budget_versions, 0034 tasks, 0044 `projects` UNIQUE (id, workspace_id) for composite FKs; independent of 0067–0081 — and post-conditions that RAISE on drift). Nullable columns and additive tables only; no existing policy is restated or dropped except where a new gate must be used (state which).

1. `public.shot_lists`: `id uuid pk`, `project_id` → projects CASCADE, `workspace_id` (stamped by the `fn_populate_workspace_from_project` trigger like 0040), `title text not null`, `version integer not null default 1`, `summary text`, `snapshot jsonb not null default '{}'` (written on "Save": the list's scenes+shots as they were, for history), `archived_at timestamptz`, audit columns + `touch_updated_at`; `UNIQUE (project_id, title, version)`; index on project_id. RLS: select = workspace + live project (the 0040 shape); insert/update = `has_active_membership() AND can_edit_shot_lists(project_id)`; no delete policy (archive only).
2. `public.shot_list_items`: `id uuid pk`, `shot_list_id` → shot_lists CASCADE, `project_id`, `workspace_id`, `scene_id` → scenes CASCADE (nullable), `shot_id` → shots CASCADE (nullable), `position integer not null default 0`, audit; `CHECK ((scene_id IS NULL) <> (shot_id IS NULL))` (exactly one); `UNIQUE (shot_list_id, scene_id)`, `UNIQUE (shot_list_id, shot_id)` (partial, on the non-null column); indexes on (shot_list_id, position), scene_id, shot_id. Same RLS as shot_lists (+ delete = the same gate: removing a shot from a list is a delete here).
3. `public.edits`: `id`, `project_id`, `workspace_id`, `shot_list_id` → shot_lists CASCADE, `title text not null`, `version integer not null default 1`, `summary text`, `parent_edit_id` → edits SET NULL, `items jsonb not null default '[]'` with `CHECK (jsonb_typeof(items) = 'array')` (each item `{ id, scene_id, shot_id, label, notes }`; the 0044 task_templates precedent and its three reasons: whole-array writes on Save, sibling references inside one document, one shape on both backends), `snapshot jsonb`, `archived_at`, audit; `UNIQUE (project_id, shot_list_id, title, version)`. RLS as shot_lists.
4. `public.projects`: `active_shot_list_id uuid REFERENCES shot_lists(id) ON DELETE SET NULL` (the 0036/0037 `budget_active_version_id` shape — structural one-active).
5. `public.tasks`: `scene_id uuid REFERENCES scenes(id) ON DELETE SET NULL`, `shot_id uuid REFERENCES shots(id) ON DELETE SET NULL`, indexes. `public.assets`: `scene_ids uuid[] not null default '{}'`, `shot_ids uuid[] not null default '{}'` (the client's existing local shape; note the integrity trade-off in the header — arrays cannot be FKs — and add a nightly-safe orphan sweep note, not a trigger).
6. `public.budget_versions`: `shot_list_id uuid REFERENCES shot_lists(id) ON DELETE SET NULL`; and `summary text` IF the controller's morning message says F8 = column (the chip prompt will say; default: add it now, nullable — a column nobody writes yet is harmless and saves a second migration on the same table).
7. **The gate.** `create function public.can_edit_shot_lists(p_project uuid) returns boolean` SECURITY DEFINER, STABLE: true when `current_app_role() IN ('admin','manager')` OR the project is unstaffed (the `can_write_project` opening) OR `project_role_for(p_project) IN ('manager','member','reviewer')`. Grant to authenticated; revoke from anon. Header: why reviewers are in (Audrey, D8, 2026-09-29) and that this gate must NEVER be reused for scenes, shots, tasks or budgets.
8. **Set active and archive**, manager/admin only, as SECURITY DEFINER RPCs with explicit checks (the Phase-5 approval pattern in the handbook): `set_active_shot_list(p_project uuid, p_list uuid)` (checks `current_app_role() = 'admin' OR project_role_for(p_project) = 'manager'`, checks the list belongs to the project and is not archived, writes `projects.active_shot_list_id`), `archive_shot_list(p_list uuid)` (same check; refuses the active list; sets `archived_at`), `archive_edit(p_edit uuid)`. A BEFORE UPDATE trigger on shot_lists refuses a change to `archived_at` outside the RPC (set a GUC in the RPC and test it in the trigger — the 0059/Phase-5 GUC-arm pattern) so the plain UPDATE policy cannot be used to archive.
9. **Backfill**, in the same migration, idempotent: for every project with at least one scene, insert one shot_list ("Shot list 1", version 1, summary 'Created from existing scenes'), items for every scene (position = scene_number order) and every shot (position = shot_number within its scene), and set `projects.active_shot_list_id`. Post-condition: every scene and shot of such a project is in exactly one item of that list.
10. Realtime and edit_history: leave both alone (scenes/shots are in neither; say so in the header; S3c's draft lives in the provider).

**pgTAP:** `84_shot_lists.sql`, `85_shot_list_items.sql`, `86_edits.sql` on the 48_scenes / 45_budget_versions patterns (RLS enabled + forced, no FOR ALL, the exact policy count, the stamping trigger, the CHECKs, the FKs, the gate: a reviewer CAN insert a shot_list and CANNOT insert a scene; a member CANNOT set active; a manager CAN; anon nothing); probes added to `01_projects` (the new column), `04_tasks` / `03_assets` (the new columns), `45_budget_versions`. Every new table into `RLS_TABLES`. Apply 0084 to DEV only, AFTER the controller has applied 0072, 0081, 0082 and 0083 there (the hand-off `po-merge-2026-09-30.md` says whether that is done; if not, stop and ask the controller): `supabase db query --linked --file supabase/migrations/0084_shot_lists_and_edits.sql` (one file), then prove by query (`schema_migrations` row inserted the house way, the backfill counts on the seeded smoke workspace `5eed0000-…`); write the exact staging command into "Waiting on Audrey". Never `db push`.
