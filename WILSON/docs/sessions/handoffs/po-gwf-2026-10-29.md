## 3. Done and verified

1. **The mechanism, measured.** `serveClip` (`gateway/src/doors/clips.mjs`) counted a response into its viewing in `done()`, which runs on the pipeline's end: the response's `finish`, after the socket's write callbacks. The harness's `request()` resolves on the client's `end`, which needs only the bytes. Nothing orders the two, so the test's `W.clock.t += 60_000; tick()` could run between them and close the row (`lastAt` still the second request's, exactly 60 s before) with the second range missing. The test already consumed the whole body before the tick; the brief's first branch (await the body, then tick) was already true, so the race is the door's: it could close a row before a response it had fully answered was counted. Not Linux's alone: rarer on this machine, which fits its never having shown in a Windows suite run.
2. **The fix (`3a3ecd88`).** The counter transform calls `viewings.served()` for each chunk before passing it on, where `sent` and the outside bytes budget count it, so the client cannot hold a byte the row lacks. `served()` no longer moves `lastAt`; the new `settled()`, from `done()`, does, as `served()` did there before (a response's end is activity, when it served bytes). Totals, offsets, coverage, the 60 s and five-minute rules and the `clip_served` log line are unchanged; an over-budget chunk is counted as before. Verified by the table above and the file's 45 tests.
3. **The control.** *"the row holds every byte the client has, even when the response's own end lands after the idle check (the control)"*: `makeWorld`'s new `onRequest(req, res)` hook lets it hold the second response's `finish` and `close`, so the door's `done()` cannot run before the tick. It asserts the client has every byte and the door's end has not run, ticks, reads the row whole, then releases and checks the late end opens no row. Red on `a351adc8`'s gateway with the CI figures (10 of 10, and once more with the final file), green after. Its waits allow 10 s and the test 30 s, so a slow runner is no failure.
4. **The flaky test** now also asserts both ranges arrived whole (206, 524,288 and 524,305 bytes), so a cut response can never pass for this race again, with a comment on why the row is whole at the tick.
5. **The record.** OUTSTANDING: the dated line closing the CI-flake thread under the gateway's tests entry (the entry stays for the Windows time-outs and the journal's EPERM); a new entry, *A response open longer than the idle minute is counted only up to its viewing's close*; the session log's row; markers 4 → 4; `gateway/test/gw4Docs.test.mjs` and `docs.test.mjs` green.
