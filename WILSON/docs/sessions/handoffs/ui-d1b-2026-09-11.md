## 5. Traps hit

1. **A fifth pin, not in D1's list.** `localMediaWiring.test.js:180` asserted
   Files' bars equal Team Members'. It was written when both were 200/150 and
   had nothing to do with either page's chrome; moving Team Members alone
   turned it red. It asserts Files ≠ Home now. Any bar change should grep for
   `.bars.top` across `src/lib/*Wiring.test.js`, not only `pageBars.test.js`.
2. **The kit Dialog is not modal for the keyboard, and only for the keyboard.**
   Q17 gave it Escape, the stack and the busy lock and nothing else: no focus
   trap, no `inert` on siblings, no initial focus. The backdrop blocks every
   pointer event, which is why a mouse-driven check passes and why the gap is
   invisible until someone presses Tab. A native confirm was fully modal, so
   converting one is a C1 regression for keyboard users unless the CALLER
   closes the gap, and `inert` on the caller's own surface must cover
   everything the keyboard can reach from the dialog — the card alone leaves
   the tab rail and the backend switch live. `inert` also blurs the trigger
   the user just pressed (focus goes to `<body>`; the next Tab lands on the
   dialog's X; Escape still works from there). Every future W9 conversion
   needs this; every existing Dialog caller (the pet dialogs, Team Members'
   invite, Bins, UpdatePrompt) has the gap. A busy, locked dialog can be torn
   down from the keyboard by activating another tab behind it; the
   in-flight bridge call then lands on an unmounted card, and its success
   path still reloads the window — by design (see §3).
3. **`window.electronAPI` present means "desktop build": the URL is ignored.**
   To photograph the Storage dialogs the browser needs a stand-in bridge, and
   with one installed the app boots on Home whatever the path says, and the
   nav strip's own "App settings" item sits under `.wilson-chrome`, so
   Playwright's `getByRole('button', { name: /app settings/i }).first()` picks
   the covered one and times out. Click the largest visible button by text
   through the DOM instead (§7 describes the script; it is not committed).
4. **The Dialog's 200ms fade starts at opacity 0** (`animation … both`), and
   Playwright's `waitFor()` resolves as soon as the node is attached and has a
   box, so a screenshot taken straight after shows no dialog. Settle ~500ms.
5. **`.s-data` is light-page ink** (D1 §5, the currency-menu blocker), so
   `PathLine` cannot be reused inside a dark Dialog. The reset body renders
   the helper's text in the dialog's own ink with `whitespace-pre-wrap
   break-words`; `break-all` would split the prose mid-word, `pre-line` would
   drop the two-space indents.
6. **Accessible names collide across the backdrop, and `inert` does not
   help a role query.** The card's "Close folder" trigger and the dialog's
   "Close folder" confirm are both in the DOM while the dialog is up (plus
   the kit's X, `aria-label="Close"`), and Playwright's `name` is a
   case-insensitive substring by default. Measured with the close dialog up:
   `getByRole('button', { name: 'Close folder' })` → 2 (strict-mode
   violation), `{ name: 'Close' }` → 3, `{ name: 'Close', exact: true }` → 1
   (the X); with the reset dialog up, `'Close folder'` → 1, and that one is
   the inert trigger. Scope every dialog query `within(dialog)`; the render
   test does.
7. **jsdom does not enforce `inert`.** A `fireEvent.click` still reaches a
   button inside an inert subtree, which is what made the stranded-dialog
   case writable at all; assert the attribute, and prove the interactive
   claim in the browser (round 2 did). And `[inert]` is unique in that test
   only because `GatedAction` is mocked: the real one renders its own
   `inert` span for every denied control.
8. **Source-text pins cut both ways** (D1 trap 2, again). The negative pin on
   the call form is safe from a comment that names the API without a paren;
   the positive pin on the danger button was satisfiable by a comment quoting
   it, so it now carries a refusal of any comment line with the pattern.
9. **The busy flag is card-wide.** One `busy` covers the folder picker, the
   seed, the reset and the dialogs; the dialog's lock is that flag. A second
   dialog cannot open while one is pending because every ask-handler checks
   `busy` first and `pending` is one slot, not a stack.
10. **`key={idx}` on the department rows** (pre-existing). Removing a row
    re-keys the ones below it; the surviving instance keeps `draft` and
    `editing` from the old name. `removeConfirm` is reset in the same event
    as the removal, so no dialog for the wrong name can appear (traced by
    round 1), but the `draft` carry-over is an older defect and not this
    bundle's.
11. **The Storage tab logs a React key warning with no dialog open** — from
    `Card`'s `{children}` array, pre-existing, bisected by round 1. Not this
    bundle's; do not chase it from the dialogs.
12. **"150px returned" is a tall-window number**, and tester-mode
    measurements are signed-out measurements. The 200/150 row reaches its
    caps only from 891px tall and Home from 1076, so any headline gain must
    say at which height; and a Settings section whose contents depend on a
    session (`PasswordSection`) is shorter in the dev server than in Audrey's
    app. Say which state a number was measured in.

## 7. For other sessions

- **Kit request (Foundation, needs Audrey's ruling against Q17):** `Dialog`
  should make everything outside itself `inert` while mounted (a portal to
  `document.body` plus `inert` on its siblings, or a focus trap), and move
  focus into itself on open. The concrete cost of not doing it, measured:
  with a Settings confirm open, six Shift+Tabs reach the storage-backend
  switch and Enter switches the backend under the dialog. Until then every
  caller that converts a native confirm must set `inert` on everything the
  keyboard can reach — on Settings that is the tab panel, which means lifting
  the card's `pending` up a level — and a dialog rendered inside the thing it
  guards (the department row) cannot.
- **Lane C:** the five rows still at 200/150 (`project-manager`, `rate-card`,
  `project-files`, `dashboard`, `admin-terminal`) move to their W10 geometry
  in each page's own conversion commit; `pageBars.test.js`'s `RESTING` and
  the "lane-C rows stay 200/150" case move with them. Files takes the tool
  geometry 95/8 per Q8(b); `localMediaWiring:180` (Files ≠ Home) survives.
- **Foundation:** `src/layout/pageBars.js`'s header, property 3, still says
  "Settings is 200/150 and stays 4:3 the whole way down" — now about
  Projects; Settings is 120/80 and 3:2. Property 1 ("every other row is small
  enough that its cap wins at every window size") was already untrue: the
  200/150 cap wins from 891px, the 120/80 cap from 740. Two lines when the
