## 5. Traps hit (the brief did not say these)

- 🚨 **A failing `supabase db query --linked` EXITS 0** and prints its error to
  stdout. An exit code is not a result here; read the output.
- 🚨 **Retrying against a project whose temp login role another session is
  rotating trips the pooler's circuit breaker** ("too many authentication
  failures, new connections are temporarily blocked"), which then blocks the
  project for minutes. My own retries caused it. Stop and wait; do not retry.
- **`npx supabase` has no Windows binary here.** The CLI is on PATH via scoop
  (`C:\Users\Audrey\scoop\shims\supabase.exe`, v2.90.0). Call `supabase`
  directly.
- 🚨 **The tool harness collapses backslashes inside a bash heredoc** (the A1
  hand-off said this; I hit it three times anyway). A `\n` written that way
  becomes a real newline and breaks the JavaScript or regex it lands in. Write
  anything with an escape using the Write tool, or avoid escapes entirely
  (`String.fromCharCode(10)`).
- 🚨 **A data-modifying function and a read of its effect in ONE statement
  share the pre-statement snapshot.** `ok(restore_soft_deleted(…) AND (SELECT
  count(*) …) = 1)` failed on dev although the restore worked. Separate
  statements. `AND` also gives no left-to-right guarantee.
- 🚨 **PostgreSQL applies the SELECT policy to rows a DELETE reads through its
  WHERE clause.** A soft-deleted phase is invisible, so `DELETE FROM phases
  WHERE id = …` matches ZERO rows — my first FK probe deleted nothing and read
  the FK action as broken. Once a row is in the trash only
  `purge_soft_deleted` (service_role) can hard-delete it.
- 🚨 **`date` IS legal as a `RETURNS TABLE` column name.** R1 read the grammar
  as forbidding it and could not test it. Measured: `pg_get_function_result`
  on dev returns `TABLE(… date date …)`. Settle a grammar question with the
  database, not with the grammar.
- 🚨 **TWO `tap-all` RUNS AGAINST DIFFERENT PROJECTS STILL RACE.** The A1
  hand-off says two full runs on two projects at once are "fine but slow"; that
  is WRONG, and this session measured it. The CLI's temporary login role is per
  LOGIN, not per project, so concurrent runs rotate each other's credential
  whatever project they target. Run concurrently, dev reported 3 problems and
  staging 2, with planned assertion counts 25 BELOW the true total — the
  signature of suites that never ran. Re-run one at a time, each was **70/71
  clean, 1286/1287**, the only red being the known suite-66 transient. Two
  lessons: run them sequentially, and **never pipe `tap-all` through `tail`** —
  the truncation hid the per-suite QUERY FAILED lines the protocol says to read
  instead of the summary, and a shrinking `planned` count is the tell.
- **A pgTAP breaker can be run safely against a SHARED project.** `db query
  --file` with the mutation BEFORE the suite puts it inside the suite's own
  `BEGIN … ROLLBACK`; DDL is transactional. Two other tracks were live on
  wilson-dev throughout and nothing leaked — verified clean after every round.
- **A post-condition breaker needs its own explicit `BEGIN … ROLLBACK`**,
  because it runs outside a suite.
- 🚨 **THE THEME OF THIS SESSION: three separate instruments were wrong, and
  only a breaker found each.**
  - A probe was a FALSE PASS under the exact mutation it existed to catch —
    with the FK switched to CASCADE the row is deleted, so the scalar subquery
    yields NULL and `is(NULL, NULL)` passed. Count rows matching the whole
    condition instead of reading a column.
  - Two source pins matched the WRONG OCCURRENCE of an expression that appears
    twice in the file. Pin the whole assignment.
  - A `useCallback` extractor paren-matched from `useCallback(` and so carried
    a whole neighbouring function; its controls could not see it. The real
    control is "no extract contains a second `useCallback(`".
  - A walkthrough label check resolved typed-in values against this session's
    own TEST FIXTURES. Search production source only.
  **Run the breaker. A pin that has never gone red is a hypothesis.**
- **`status()` cannot witness the supabase adapter's `lastError`**: its
  ordinary arm re-probes and overwrites it, and the no-client arm is only
  reachable through `resetSupabaseAdapter()`, which clears it first. Some
  module state has no behavioural vantage point; say so and pin the source.
- **Nothing was refused by the desktop app's classifier this session** — dev
  DDL, dev history writes, the staging `link`, staging DDL and staging history
  writes all ran. The wall is per command, as the protocol says.
