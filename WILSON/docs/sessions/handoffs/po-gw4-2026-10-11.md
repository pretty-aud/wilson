## For GW5 (what to attack in the release path)

1. **The redirect chain.** `releaseFetch` follows at most three redirects, every hop's host exactly one of `github.com`, `release-assets.githubusercontent.com` and `objects.githubusercontent.com` after the URL parser's own normalisation, HTTPS on 443 only, no user info; the body is capped by its declared length and as it streams, and a body cut short is named. The signature is fetched from the `github.com/<repo>/releases/download/<tag>/stable.json` hop the manifest came through. Attack: a hop whose name normalises onto the list, a relative `Location`, a 304 or 206 at the end, a drip just under the 30-second silence for the 30-minute deadline, and `latest` moving to another tag between the manifest's fetch and the signature's. `gateway/test/releaseServer.mjs` plays GitHub's three hosts on loopback, every route replaceable.
2. **A stale or lower manifest.** The gateway keeps the last manifest it verified (`last-manifest.json`), refuses a strictly older one, and never takes one whose version is below it (round 2); the updater refuses one not newer than the last it swapped; one more than a day ahead of the clock is refused; the pipeline publishes only above every published gateway release. Attack: `last-manifest.json` deleted or rewritten by a local administrator (an older signed list whose version is still above the running one is then taken, with its floors), a replay of a list signed before a floor was raised, the gateway's clock, two releases with the same `published_at`, a release marked Latest by hand.
3. **The release job around the publish.** Checked in the plan job, in the sign job before the key is read, before the draft, just before the publish and after it (a higher release published meanwhile puts this one back to a draft); the read-back requires exactly the uploaded assets, each as uploaded, the artefact and the MSI held to the signed list. Attack: who can change a draft between its read-back and its publish (anyone with write access to the repository), a re-run of a failed real release (GitHub answers 404 for a draft's tag, so a re-run makes a second draft for the same tag), two runs approved within the same minutes (the after-publish check undoes the lower one, but a gateway that checked in the seconds between can have taken it), and a workflow edited on a branch (the tag ruleset and the environment's approval are the review points).
4. **Pebble's gaps.** Pebble validates from the same host over loopback, answers in seconds, and has none of Let's Encrypt's rate limits, CAA checks of a real domain, multi-perspective validation or revocation. The job proves the protocol and the door's hooks, not Let's Encrypt in production. Attack: the backoff and the six-an-hour cap against Let's Encrypt's real limits (five failed validations an hour per name and account), an outside address that changes often (each change is a new order), a CAA record that forbids Let's Encrypt, and a CA that is slow rather than stalled (each request ends at 120 s; an attempt of many requests can still take minutes).
5. **The unsigned MSI (D14).** SmartScreen warns for every unsigned build, so the warning cannot tell a planted MSI from Petal's; `SHA256SUMS` proves a download whole, not its origin; the signed version list names the installer's SHA-256 for the pipeline's own read-back, and nothing on a computer without a gateway checks it. Attack: a look-alike repository or a typosquatted asset, someone with write access replacing a published release's MSI, and whether the stories steer an admin away from both.
6. **The tar reader, as LocalSystem's input.** It refuses `:`, `<>"|?*`, trailing dots and spaces, device names with any extension, 8.3-shaped segments (`~1`) and two entries equal in another case (rounds 1 and 2). Attack: what else NTFS or Windows' path rewriting reads as another file, with Node writing through `\\?\` paths (the reviewer measured that `CON` and a trailing dot are written literally, and that a `:` stream is real).
7. **The updater's pipe from a gateway taken over.** The gateway's own account holds the pipe's key, so it can ask the LocalSystem updater for a rollback (one step back), the outside door's firewall rule (the port is checked against the office door's) and the SMB dialects. Attack what a compromised gateway account can make the updater do.
8. **The other workflows' token** (not GW4's files). `.github/workflows/rls.yml` and `.github/workflows/backups.yml` have no `permissions:` block; both only check out and use their own secrets, so `permissions: contents: read` and `persist-credentials: false` are safe there. Until the repository's Actions token setting is *Read* (walkthrough 63 §A), an install script in `rls.yml`'s npm tree could hold a token that writes releases and packages.
9. **The image as pushed.** The workflow never runs the pushed digest (its version check runs a local build), and BuildKit's builder image is pulled by a moving tag (`moby/buildkit:buildx-stable-1`). Pin the builder by digest (`--driver-opt image=moby/buildkit:<version>@sha256:…`) and run `docker run --rm "$IMAGE@$DIGEST" version` on the pushed digest: both are workflow changes no dry run here could prove (the brief allowed one), so they are left for a session that may run one.
