## 5. Traps hit

- 🚨 **`typeScale.test.js` requires every file under `src/tools/` to belong to a type-scale lane** (T1 Dog and Otter, T2 Rabbit). A new tool folder belongs to none, so the Vitest job goes red. MO1's design (§1.10 "PINS TO UPDATE") does not list it; whoever lands `src/tools/moth_v0.1.0/` first adds the lane (one regex line). Not touched here (the brief's file list).
- 🚨 **Run the repo's own binaries from `WILSON/`** (`./node_modules/.bin/vitest`, `./node_modules/.bin/vite`). A bare `npx vitest` from the repository root downloaded Vitest 5.0.5, ran the e2e specs and left caches in a stray root `node_modules` (removed).
- 🚨 **Frame lateness is not frame cost.** At 60 Hz a healthy frame arrives up to 16.7 ms after it is asked for, so a governor that judges "headroom" on lateness never leaves light mode; the exit judges script work, the entry judges what the person saw.
- 🚨 **Do not feed the governor the frames of a settling layout**: the worker holds a core, frames come late, and light mode cannot fix that (measured: it dropped to light during the first settle and stayed).
- The worker must not post every batch: posting at most every 32 ms took feedback while streaming from max 124 ms to 66 ms.
- `forceSimulation()` starts a d3-timer the moment it is made; `.stop()` at once (done), or a stray frame or timeout fires.
- Module workers do not load from `file://`; serve the build over HTTP to measure.
- On a 4-vCPU box only two workflow agents run at once; an agent silent for six minutes is usually composing a long reply, not dead (check its transcript before restarting).
