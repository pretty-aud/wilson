## Step 0 — set aside, never lost: the design (written before the code)

Audrey's ruling (a): *"a version shows exactly its own schedule."* Opening a
version makes the live Timeline and Budget equal to it; rows that are not
part of it are SET ASIDE and come back — the same rows, with everything on
them — when a version that holds them is opened. Part 1 built the opposite
(they stayed, and Save folded them in); this replaces it.

### 0.1 The state: a column, `set_aside_at`

`set_aside_at TIMESTAMPTZ` on `tasks`, `phases` and `milestones` (migration
**0090**, suite **92**); the same field on the Local Server's rows and the
dev fixtures'. A row is exactly one of:

| State | Stamps | Where it shows |
|---|---|---|
| live | neither | everywhere, as today |
| set aside | `set_aside_at`, no `deleted_at` | nowhere; kept whole, never listed in a trash, never purged |
| trashed | `deleted_at` | the ordinary trash (cloud: purged at 30 days) |

A trashed row is never also set aside: trashing clears the stamp (a trigger
on the cloud, the same rule on the other two), so anything taken out of the
trash comes back live.

**Why a column, not the provider-level scope** (the alternative the brief
names; measured against the code, not assumed):

1. It must outlive the open version. Under a lock nothing is open (part 1's
   R1-10), and after a reload with no version open the rows must STILL be set
   aside (constraint 6). A scope computed from the open version's snapshot
   would show every one of them again the moment no version is open.
2. Readers outside the provider must hide them (constraint 3): the
   Dashboard's cross-project My tasks, the Local Server's mirror files and
   manifest counts. They can filter a stored state; they cannot compute a
   scope from snapshots they may not read (a member reads no bid versions).
3. One field, stored and tested the same way on the three backends
   (constraint 5).

"Which open set it aside" is NOT stored: nothing would read it. The open's
undo step carries the ids it set aside; the delete-version question computes
"held only by this version" from the snapshots.

### 0.2 Who writes it, and how

- **Only past the money gate** (D8): on the cloud a BEFORE INSERT OR UPDATE
  trigger on each of the three tables refuses a CHANGE of `set_aside_at` (or
  an INSERT carrying one) unless `can_access_project_money(project)` or the
  service role (0089 §3's shape: an unchanged value always passes). Trashing
  clears it for anyone allowed to trash.
- **One writer**: the RPC `set_aside_schedule_rows(p_project, p_on, p_tasks,
  p_phases, p_milestones)` — SECURITY INVOKER (the tables' own UPDATE policies
  and the trigger apply), the three tables in one transaction, trashed rows
  untouched, returns the stamp it wrote. The Local Server gets `POST
  /api/rabbit/projects/:id/set-aside` (one bundle write); the fixtures the
  same method under their money gate.
- **The ordinary writes never carry it.** The cloud adapter strips it from
  task, phase and key-date upserts and patches; the Local Server strips it
  from its POST/PATCH bodies (its upsert MERGES, so a stale row re-sent with
  `set_aside_at: null` would otherwise bring a row back unasked); the
  desktop-to-cloud copy (`runMigration`) strips it, so desktop rows arrive
  live (bid versions are not migrated: nothing on the cloud could bring a
  set-aside row back).

### 0.3 Reading it: hidden everywhere (constraint 3)

**RLS is untouched.** Filtering in the SELECT policies would repeat the
soft-delete trap (a set-aside row could no longer be read back to bring it
back, and a PATCH of it would be refused).

**Every loader splits.** Each adapter's `loadProject` keeps `tasks`,
`phases`, `milestones` = the LIVE rows and returns the set-aside ones under
four new bundle keys — `setAsideTasks`, `setAsidePhases`,
`setAsideMilestones`, and `setAsideDependencies` (the edges touching a
set-aside task or phase, which would otherwise draw to nothing and count in
the dependency checks) — through one pure helper. So every in-memory reader
of `ctx.tasks`, `ctx.phases`, `ctx.milestones`, `ctx.dependencies` and every
selector over `bundle.tasks` hides them WITHOUT being changed. That is the
point of the split: the sweep found 60-odd readers there.

The readers, on all three backends (a sweep of every reader; the hand-off's
end says which changed):

| Reader | Backend | What happens |
|---|---|---|
| `loadProject` (phases, tasks, key dates, dependencies) | cloud, Local Server, fixtures, Drive | split by the shared helper |
| every `ctx` reader: the Timeline (gantt, rows by every grouping, minimap, Summary band, dependency drag, phase pickers, key dates), Tasks (table, kanban, counts, CSV export, key-date rows), Budget (the three tiles, every report tab, Crew, Client view and its print, the Expenses pickers), the Project summary tiles, Assets / Scenes / Levels / Experiences task counts and relations, Team counts, the task popup, New task, the dependency guard, the asset warning, intake counts, the selectors (variance, rollup, critical path), the client-side manifest counts | client | nothing to change: they read the live arrays |
| `listMyTasks`, `listPhasesByProjects` (the Dashboard's cross-project list and its task popup) | cloud, fixtures | filtered (on the client side of the read, so a database without 0090 still answers) |
| `applyRealtimeEvent` (another window's writes) | cloud | learns the stamp: an UPDATE that sets or clears it moves the row and its edges between the live and set-aside arrays; the project row's open-version pointer arriving makes a window past the money gate re-read the versions (they are not broadcast, S5-02) |
| `revertHistoryEntry` (Edit history) | client | refuses a set-aside row with a sentence instead of re-adding it as if lost |
| `planOpen` / `reviveBudgetRow` | client | a set-aside row is BROUGHT BACK, never revived or re-made |
| `mirrorProjectDatabases` (`tasks.json`, `timeline.json`), `buildProjectManifestFor` | Local Server | filtered |
| `runMigration` (desktop → cloud) | client | stamp stripped: rows arrive live (above) |
| `WorkspaceTakeout` (an admin's CSV backup), `rabbit:archive-local-data` (the desktop backup) | cloud, Local Server | unchanged ON PURPOSE: a backup keeps every row; the takeout's `set_aside_at` column says which are set aside. For Audrey. |
| `purge_soft_deleted`, `milestones_trash_index`, `soft_delete_row` / `restore_soft_deleted`, the fixtures' and Local Server's key-date trash | all | unchanged: they read `deleted_at` only, so a set-aside row is never listed and never purged — PROVEN in suite 92 and the contract tests (constraint 2) |
| the pet and agent, D.O.G., O.T.T.E.R., edge functions, SQL views (none exist) | — | never read these rows (the agent's `summarize_project` is dead code) |

### 0.4 Opening a version (the plan, constraint 7)

`planOpen` takes the set-aside rows too and returns, beside part 1's
`update` / `create` (revive or re-make) / `settings` / `rates`:

- `bringBack` — rows the version holds that are set aside now;
- `setAside` — live rows it does not hold, less those kept (0.5).

The composite, ONE undo step, in this order: close the open version · bring
back (one RPC) · revive trashed / re-make lost rows (part 1) · write the
schedule fields · set aside (one RPC) · settings, rates · select · open.
Undo replays each step's inverse: what it set aside comes back, what it
brought back is set aside again, every value restored.

**Only versions with a timeline count as holders.** A version saved before
S5 ("no timeline captured") cannot be opened, so it can never bring a row
back: "held by another version" (0.5, 0.7, 0.8) means held by a version that
can be opened.

### 0.5 The questions before an open (constraints 4 and 8)

1. **Unsaved first** (F2): if the open version has unsaved changes —
   *Save to Mid ROM · v2* / *Discard changes* / *Cancel*; if NO version is
   open and the live schedule matches no saved version — *Save as new
   version…* / *Discard* / *Cancel*. Cancel first and focused. **Discard**
   deletes the live rows that are in NO saved version, the ordinary way, and
   says so by count and name, rows with work first (constraint 8); the open
   then does the rest. Discard and the open are one undo step.
2. **Then the open itself** — *Edit "Mid ROM · v2"?* — naming what leaves and
   what returns ("12 tasks and 1 phase that are not part of it are set
   aside; 9 of its own return. Nothing on a set-aside row is lost.").
   **Constraint 4**: when a row about to be set aside has WORK on it — a
   task's `logged_days` > 0, comments on it (`comments.entity_type` task or
   phase), files linked to it (`files.task_id` / `phase_id`, the desktop's
   `managedFiles.task_id`); key dates carry none of these — the question names
   each by its counts ("Lighting pass 2 — 1.5 days logged, 2 comments") and
   offers **Keep these in Mid ROM · v2** (they stay on the Timeline as its
   unsaved changes; a kept task keeps its phase with it). Answers: *Cancel*
   (first, focused) and *Edit this version*; the keep is a checkbox in the
   question, OFF by default.

   Why that shape (laws-of-ux, design-direction): one verb per question —
   hers, *Edit this version* — keeps the question the same shape with or
   without work (Law of Similarity), and the work choice sits beside the
   names it is about (Proximity, Working Memory). Why OFF: setting aside is
   the SAFE answer — nothing on the row is lost (constraint 1) — while
   keeping makes the version dirty at once, and a quick Save would fold
   another bid's tasks into this one: the very fault ruling (a) removed
   (Cognitive Bias: the default is the answer whose mistake costs least).
   For Audrey.

### 0.6 Under a lock (constraint 6)

Nothing opens while a budget is active, so nothing is set aside or brought
back; the Remove verb (0.7) is off (no version is open). **Set budget active
locks the SELECTED bid AS SAVED**: the live schedule becomes that version —
it is opened first, inside the same undo step and behind the same questions,
when it is not the open one (an open version with unsaved changes asks
Save / Discard / Cancel first) — then locked and closed. So the schedule
under a lock is the locked version's rows plus whatever is made in
production. A version with no timeline captured locks without loading (the
Timeline stays as it is, and the question says so).

### 0.7 Removing a row while a version is open (constraint 9)

The person's delete verbs (`ctx.deleteTask`, `deleteTasks`, `deletePhase`,
`deleteMilestone`) decide per row while a version is open, no budget is
active and the person is past the money gate: a row another saved version
holds is **set aside** — *Remove from this version* — and stays in that
version; any other row is **deleted** the ordinary way. The confirm says
which, by name and by the versions that hold it (a pure copy module,
`membershipCopy.js` the model); the paths with no confirm today (a Tasks
row's delete, the task popup) say it in the undo toast, and ask first when
the row has work on it. History ops keep the RAW deletes (registered in
`mutationsRef`), so an undo or redo never routes. A member never sees
versions (F10): their delete is the ordinary one, and opening a version that
holds a trashed row restores it from the trash (part 1's `reviveBudgetRow`).

### 0.8 Deleting a version (constraint 10) — decided here, for Audrey

Rows only that version held, set aside now, would be stranded. **They are
deleted with it, the ordinary way**, named in the delete question by count
and name, rows with work first ("3 tasks only this version holds go with it:
… — Lighting pass 2 has 1.5 days logged. Undo brings back the version and
them."), in the same undo step. Why: the version is the document that held
them; deleting it says the bid is no longer wanted, and bringing its rows
into another bid would silently change that bid (the R1-05 fault again).
The alternative for her to choose instead: bring the rows with work back to
the Timeline and delete only the rest. Rows only the deleted version held
that are LIVE (it was the open one) simply stay: it closes, they remain.

### 0.9 What "deleted the ordinary way" is, per backend (copy must be true)

R.A.B.B.I.T.'s "Recently deleted" covers **key dates only**. Tasks and
phases are trashed on the cloud and the fixtures (no list shows them; Undo
and the Edit history bring them back; the cloud purges at 30 days) and
HARD-deleted on the Local Server (Undo re-adds them). The questions say
"Undo brings them back", and "Recently deleted" only for key dates. For
Audrey: tasks and phases have no Recently deleted list.

| # | Constraint | Proof | Plant that must fail it |

| 2 | the trash is not the store | suite 92: purge leaves a set-aside row stamped 60 days ago (CONTROL: a trashed one goes); the key-date trash index omits it; fixtures and Local Server trash lists omit it | the stamp written into `deleted_at` |

| 4 | work never hidden unasked | the plan names rows with logged days, comments, files; keep leaves them live and the version dirty | the work test reading only logged days |
