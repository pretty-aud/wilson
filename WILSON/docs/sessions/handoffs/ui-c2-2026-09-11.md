## 5. Traps hit

**0. THE KIT'S `Input` EATS ESCAPE TWICE, AND THE SECOND BITE IS THE ONE THAT
GETS YOU.** D1 recorded the first half (`onBlur` fires on the cancel path, so
use `onCommit`). Two more halves cost this session two regressions:

- **It never forwards Escape to your `onKeyDown`.** `Input.jsx:68-72` runs
  `esc.cancel(e); return` *before* `onKeyDown?.(e)`, and `cancel` calls
  `stopPropagation()`. So a call site that had an Escape branch loses it
  silently on adoption, and a bubbling handler on an ancestor never runs
  either. **The working spelling is `onKeyDownCapture` on the wrapper.** Two
  call sites here lost their Escape exit this way, and one of them — the
  subject rename row — had no other exit.
- **Its revert is a call to your `onChange`.** `cancel` does
  `onChange?.(initialRef.current)`. If that `onChange` recreates the state
  object the field lives in (`setLinkPanel({ value: v })`), Escape **re-opens
  what your capture handler just closed**; if that `onChange` is a write, as
  on a date field, **Escape issues a PATCH**. Use a functional update that
  refuses to resurrect a closed panel, and guard a write on the value actually
  differing from the persisted one.

It also **blurs on Enter before calling `onKeyDown`**, so a field you can type
a run of entries into loses focus after each one; put the focus back.

**0b. `title={undefined}` does not remove a tooltip from `StatusDot`, and the
sibling trick next to it works.** `role` and `aria-label` are not destructured,
so they ride in `...rest`, React drops `undefined` attributes, and passing
`undefined` really does remove them. `title` **is** destructured, straight into
`title ?? name` — and `??` only tests null and undefined, so `undefined` gives
you the status name back. **`title=""` is the only spelling that works today.**
Four "decorative" dots kept a tooltip, including the card's stretched 3px edge,
which showed one across the whole top of every card.

**0c. Nothing in this app sets `color-scheme`, and Q1 is walking date fields
onto a dark ground.** Without it Chromium paints `<input type="date">`'s picker
indicator as a dark glyph on a dark well and opens its calendar in the
light-mode chrome — a near-white floating panel, which C9 forbids outright.
Fixed locally here (`.dash-date`); **filed as a kit request, because
R.A.B.B.I.T. has about a dozen more date fields still to move.**

**0c-bis. A tie with the kit is not decided by the rule you are reading.**
`.dash-tb-quiet` was three units, which beats `.ui-iconbtn` (0,1,0) at rest
and **ties** `.ui-iconbtn:hover:not(:disabled)` (0,3,0) — and a tie loses
here, so the control stopped receding exactly when the pointer reached it.
**Look up the kit rule you are overriding and count THAT selector**, not the
base one. `dashboardCss.test.js` enforces a floor on the page side and says
plainly that a floor is all it is.

**0d. A page stylesheet is emitted BEFORE the kit, so it loses every
specificity tie.** Measured live: `settings.css`, then `dashboard.css`, then
`index.css`. Both page sheets and the kit put their rules in
`@layer components`, so a `.dash-*` rule that merely ties a `.ui-*` rule does
nothing, silently. `dashboardCss.test.js` now fails any page rule that targets
a kit element with fewer than two compound units. (The comment that used to
guard this was wrong twice over: it defended against a selector that does not
exist and miscounted both sides.)

**0e. `getComputedStyle` LIES ABOUT `:hover` in the Browser pane.** Plan §7
warns that an undisplayed pane freezes style recalc; what that looks like in
practice is `el.matches(':hover') === true` while `getComputedStyle(el).color`
still reports the rest value — so a hover fix measures as broken and a hover
regression measures as fine. Both this session and review round 2 lost time to
it. **Verify a hover by SCREENSHOT** (paint is not frozen), or by reading the
rules out of the CSSOM; never by computed style.

**1. A Dialog cannot honour a synchronous veto — unless it answers the veto
first.** `TaskDetailPopup` (R.A.B.B.I.T.'s) deletes through
`if (ctx?.deleteTask?.(task.id) !== false) onClose()`, so the Dashboard's
callback must return a value *now*. W9 says convert the confirm; a Dialog is
asynchronous. The resolution is to **always return `false`** — "not deleted,
keep yourself open" — raise the Dialog, and have the Dialog close the popup
itself on confirm. Cancel then leaves the popup open, which is what a cancelled
`window.confirm` did. **Any lane converting a `window.confirm` that sits behind
a callback with a return contract should do the same rather than edit the
component that reads it.** Checked and clear: `TaskDetailPopup` registers no
document-level Escape handler, so the kit's modal stack is uncontested.

**2. A shared component with a hard-coded `surface` breaks the moment one of
its hosts changes ground.** `ProfileSection` is mounted by SettingsPage *and*
DashboardPage and writes `surface="light"` on every kit control. On `paper`
those resolve `--color-ink-light`, which is `#1c1917` — the paper itself — so
the whole tab renders black on black. D1 filed the fix (kit request 6) and it
has not landed. The interim is a scoped token bridge; **see §6**, because it is
not free.

**3. `.s-profile-empty` matched the wrong component.** Both SettingsPage and
DashboardPage mount `ProfileSection`, so a bare
`document.querySelector('.s-profile-empty')` in a browser probe returns
*Settings'* copy — which is on the light ground and correctly `#1c1917`. It
looked exactly like the bridge had failed. **Scope every probe on this page to
`.dash-profile-bridge`.** The same duplication is why `authSelectors.test.js`
pins this file's `<ProfileSection />` call and its
`display: tab === 'profile' ? 'block' : 'none'` string: two `getByLabel`
values collide in Playwright because the profile tab is in the DOM on every
authed page. **Do not reformat either string.**

**4. A `<select>` sizes itself to its widest option and then shrinks, and it
clips instead of eliding.** `text-overflow` does nothing on a `<select>`. Three
of them will not share a 300px column (measured: 85 + 97 + 103 against 284px),
