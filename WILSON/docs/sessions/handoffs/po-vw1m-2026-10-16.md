### What the measuring found that the brief did not say

1. **Three delete behaviours, not one.** The cloud deletes a task with its main asset (`tasks.asset_id … ON DELETE CASCADE`, 0000:178 and 0034) and hides it while that asset is in the trash (`tasks_select`'s asset hop, 0034:101-113, still the current policy). **The desktop never deleted the task**: its asset route only takes the asset off the task's items (`electron/main.cjs:2807-2839`). **The fixtures never hide it** (`rabbitFixturesAdapter.js:570`, `:670`). And **the provider drops the main asset's tasks from the screen on every backend** (`RabbitProvider.jsx:1961`, `:1982`; the live merge mirrors it, `realtimeMerge.js:212-217`), so on the desktop they come back at the next read (OUTSTANDING, "On the desktop, a deleted asset's tasks come back…"). The 30-day purge (`purge_soft_deleted`, 0067:339) cascades too, so a **set-aside** task dies with its main asset, against 0090's promise that a set-aside task is never purged.
2. **A task's phase comes through its main asset in four places.** The Timeline reads the task's own phase first and falls back to its main asset's phase (`effectivePhaseOf` 6664, `buildSchedule` 6558, `onMovePhaseAndChildren` 1225, `buildOverviewRows` 7552). **The Budget's *By phase* never reads the task's own phase at all**: only the main asset's (`BudgetView.jsx:1043`; the Custom tab's phase grouping 1320 and Phase filter 1294 likewise), so a task with a phase and no asset is *Unphased* there while the Timeline puts it under its phase. The Dashboard's *Phase* grouping reads the asset's phase too (`dashboardTaskModel.js:203`).
3. **Every writer of a single field still replaces "the first" item.** 0096 §7b (`fn_tasks_sync_items`), the desktop's `applyTaskWrite` and its read reconcile (`rabbitTaskItems.cjs:280-322`: **a read writes**, and a stale field reorders the items), and the fixtures' twin. So an older app, a bid version's open (`loadVersionIntoLive` → `applyLinkWrite`), the Tasks table's Asset cell and the Board's drag each **remove whichever item happens to be first**: dropping a two-asset task on *Unassigned* lands it in its second asset's column (`ProjectTasksView.jsx:1249`).
4. **Defects on the way, all touching "main".** A new task opened anywhere on the Timeline ignores the row it came from and starts with the project's FIRST asset and FIRST phase (`openNewTask` 493 → `emptyTaskDraft` 5480 reads camelCase keys, the callers send snake_case); in the asset, scene, level, experience and team groupings a dragged task bar writes the group's id into `phase_id` (1249-1254; the cloud's FK refuses it behind `.catch(() => {})`); clicking a scene, level, experience, team or *No …* header opens *Edit phase* on a stand-in phase (2846-2854); the task window's *Shot* and *Scene* file sections pass the shot's or scene's id as an asset id (`TaskDetailPopup.jsx:309`, `:339`), so they list none of its files and a desktop upload lands in `ASSETS/Untitled-Asset/`; the Budget's *By asset* has no *No asset* row, so it never added up to the project's total (1101); the Levels and Experiences tables count a task only under its main level or experience (`EntityListView.jsx:213`, OUTSTANDING P1-26).
5. **The numbers' plumbing.** CI's failure-replay list (root `rls.yml:563`) stops at 96: suites 98 and 99 are already missing from it; the coverage guard's glob is two digits (`[0-9][0-9]_${t}.sql`, `rls.yml:112`); `scripts/tap-all.mjs` sorts suites as text and filters by prefix (`… 10` would run 100 too). 0014 and 0034 call themselves "safe to re-run" with no later-migration guard: re-running 0034 after 0097 would put the asset hop back.

### The rule this session builds

**A task's items are its items.** No item of a kind counts for more than another, on any screen, in any sum, in any delete. Every reader reads the items; a task's items of a kind read in one fixed order (Q-N1). The single fields (`tasks.asset_id`, `scene_id`, `shot_id` on the cloud; the five on the desktop's and the fixtures' rows) **stay as a copy for older apps only**: the database and the backends keep writing them, nothing in this app reads them for meaning, and a write of one from an older app **adds** that item and never removes one. **Deleting or trashing an asset (or a scene, shot, level, experience) never deletes or hides a task**: the item comes off (or, in the trash, Q-N4).
