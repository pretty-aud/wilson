### 3.2 `color-scheme` — what it fixes, and the half nobody knew about

The rule, in `@layer base` beside the focus-ring scopes it copies:

```css
:root { color-scheme: dark; }
.wilson-light-scroll,
[data-surface="light"] { color-scheme: light; }
[data-surface="dark"] { color-scheme: dark; }
```

It inherits, so it is declared on the surface, not on the control, and the
dark-island rule is written last so a Dialog, Menu or Toast opening inside a
light page takes `dark` back — the same tie-by-source-order the focus ring
uses. The two page-level stand-ins (`.rs-page .ui-input`, `.dash-date`) are
left where they are: they now agree with the kit, and those files belong to
C1 and C2. `NotesView.test.jsx` pins the `dash-date` class, so the class must
stay on the element whatever happens to the rule.

**Proven in the running app** (R.A.B.B.I.T. → Salt Hours → Assets, which has
twelve `<input type="date">` with no local stand-ing): the field's own
calendar glyph goes from a dark block on a dark field to a legible light one.
`img/ui-f3-colorscheme-{before,after}-crop.png`, same cells, same page. Every
raw `<select>` in D.O.G. and O.T.T.E.R. now computes `color-scheme: dark`
too, through the page wrapper, without the kit touching them.

🚨 **THE PICKER PANEL IS A SEPARATE MECHANISM, AND IT DEPENDS ON THE
RUNTIME.** Measured, four ways:

| runtime | OS / `prefers-color-scheme` | CSS `color-scheme` | the panel |
|---|---|---|---|
| Electron 33 | light | `normal` (before F3) | **near-white** — the C9 breach |
| Electron 33 | light | `dark` (after F3) | **dark** |
| Electron 33 | dark | either | dark |
| headless Chromium (Playwright) | light | `dark` | **still near-white** |

So in the shipping runtime the CSS property IS the fix and no
`nativeTheme.themeSource` change is needed — which is the answer to the
question that change would have raised. But **headless Chromium ignores
`color-scheme` for the picker popup**, so a Playwright screenshot of the
panel is not evidence either way; do not "fix" a non-bug from one.
`img/ui-f3-panel-{before,after}-electron.png` are from a standalone Electron
probe (deleted after use), labelled as such in the walkthrough.

**The one place this property cannot satisfy C9 and the surface at once:**
the light pages' well is `well-light` (`#de9155`), a mid tone, so a UA in
`dark` mode paints a white glyph on it. The light branch is therefore `light`,
and a panel opened from a light page is the browser's near-white one.
**Measured 2026-09-11 and re-checked after the C3 merge: no `date`, `time`,
`month`, `week`, `datetime-local` or `color` input is mounted on any of the
four light pages** (home, settings, admin-terminal, help). If a lane moves a
date field onto one, that is a ruling for Audrey, not a default to inherit.

## 5. Traps hit

**1. 🚨 A GREEN SUITE PROVED NOTHING ABOUT THE FOCUS RESTORE, AND THE APP
FOUND IT IN ONE CLICK.** The first cut captured the return target inside the
effect. React applies a child's `autoFocus` during the COMMIT, which is before
any effect runs — so on every dialog that has an autoFocus field the captured
element was the dialog's own input, which is disconnected a moment later and
rejected by the `isConnected` guard. Focus fell to `<body>`. Nine tests
passed, because none of them opened a dialog with an `autoFocus` child from a
real trigger. **Capture it during render**; that is the only phase that still
sees the control the user was standing on. Plan §7's "every visual claim is
checked in the running app" covers keyboard claims too.

**2. 🚨 REACT 18 STRICTMODE MAKES INITIAL FOCUS A DEV/PROD DIVERGENCE.**
`src/main.jsx` wraps the app in `<React.StrictMode>`, so every effect runs
mount → unmount → mount in dev, and `autoFocus` does NOT fire on that second
mount (the DOM node is not recreated). With the return target fixed, the
second run found focus outside and took the first focusable control — a dev
build landing on Close where a production build lands on the field. The dialog
now remembers where it landed. **Any kit effect that moves focus, scrolls, or
registers something positional has to be idempotent across that cycle**, and
the way to test it is to render under a real `<StrictMode>`, not to describe
it in a comment.

**3. TESTER MODE CANNOT SEE MOST OF THE KIT; DEV FIXTURES CAN.** With
`VITE_DEV_AUTOLOGIN=tester` alone the Dashboard says "needs the cloud", there
are no rows, no dialogs and not one `<input type="date">` in the whole DOM —
so none of this was checkable. Adding **`VITE_DEV_FIXTURES=1`** (the
dev-fixtures session's switch) gives 8 members, 42 tasks, rate cards and
fifteen assets with date fields, and every claim in §3.4 came from it. Put
both lines in `.env.local`.

**4. THE BROWSER PANE'S VIEWPORT EMULATION BREAKS `ref` CLICKS.**
`resize_window` to 1440x900 sets the emulated viewport but the pane's
screenshot coordinate frame stayed 800x500, so every `computer` click
computed from a `ref` landed off-screen and silently did nothing. Drive with
Playwright instead (`@playwright/test` is a dev dependency and
`scripts/screenshot.mjs` shows the shape), and reset the pane with
`preset: "desktop"` when you are done. F1 trap 14 is the same trap from the
other side.

**5. A PLAYWRIGHT SCRIPT MUST LIVE INSIDE THE WORKTREE.** Node resolves
`@playwright/test` from the SCRIPT's directory, not the cwd, so a probe in the
scratchpad cannot import it. Write it under `WILSON/` and delete it after.

**6. THE NAV STRIP IS IN THE DOM BUT COVERED.** `.wilson-nav-item` buttons are
present and "visible" to Playwright while the strip is collapsed, but
`.wilson-chrome` intercepts the pointer, so a real click times out after 30
seconds with a confusing log. Drive them with
`page.evaluate(() => button.click())`.

**7. 🚨 HEADLESS CHROMIUM IGNORES `color-scheme` FOR THE DATE PICKER POPUP;
ELECTRON DOES NOT.** A Playwright screenshot showed a near-white panel with
`color-scheme: dark` computed on the input, which reads exactly like the bug
still being there. The four-way matrix is in §3.2. **The panel is not
evidence from a headless browser.** Electron 33 was the runtime that settled
it, driven with `webContents.capturePage()` and `sendInputEvent` — and the
Electron binary is NOT in a worktree installed with `--ignore-scripts`, so
run it from the canonical checkout's
`node_modules/electron/dist/electron.exe` (reading that path is fine;
junctioning `node_modules` is what plan §6.8 forbids).

**8. THE `Escape` FORWARD IS TWO HALVES AND ONLY ONE IS OBVIOUS.** `cancel()`
calls `stopPropagation()`, so forwarding the key to `onKeyDown` does NOT let
it reach a Dialog — W2's "the first press does not close" still holds, and a
test asserts it from the outside. The half that changed is that a caller's own
handler runs at all.

**9. A GUARD THAT CANNOT FIRE IS NOT A GUARD, AND THE BREAK-IT PASS IS WHAT
FINDS IT.** The focus restore shipped with a "never restore INTO this dialog"
condition. Reverting it left every test green, because the return target is
captured before the dialog's DOM exists and therefore can never be inside it.
It was removed. **Run the pass: revert each fix in turn and check the test
that covers it goes red.** On the first run it also found two tests that could
not fail — the topmost-Tab guard (both dialogs' handlers are on `document` and
the upper one runs LAST, so most arrangements are indistinguishable; the case
that separates them is a control in the MIDDLE of the topmost dialog) and
`.ui-toolbar .ui-tab`, which had no assertion at all.

**10. THE BASH TOOL'S HEREDOCS STILL CHOKE** on long CSS-and-regex blocks
(F2 trap 1). Write test files with the Write tool, or splice them in with a
Python script written by the Write tool. Also: the Write tool writes **LF**,
and every source file in this repo is **CRLF** — normalise afterwards.

**11. A `<select>` INSIDE `.ui-input` HAS NO `color-scheme` OF ITS OWN.** It
inherits from the page wrapper, which is why the rule is on the surface and
not on `.ui-input`. Putting it on the control would have missed every
hand-rolled Tailwind input in the tools, and those are the ones with no local
stand-in.
