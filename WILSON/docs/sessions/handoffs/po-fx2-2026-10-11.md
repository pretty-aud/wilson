## Item 1 — measured before building (the "let me know if there is an issue here")

Written first, before any code, and kept. Every place that reads a task's single link, what "many items" means there, the pick this bundle builds, and the alternative. The numbered questions in §6 "Waiting on Audrey" are the same picks, put to her.

### Two issues, measured

1. **The name is taken.** `public.task_links` already exists: 0000's *free-form URL links* on a task (`id, task_id, label, url, created_at`), with RLS (0004, 0013), the edit history (0012), the realtime broadcast (0016 through 0091), five suites (11, 17, 20, 72, 92), and on the client the bundle key `taskLinks`, the adapter methods `upsertTaskLink` / `deleteTaskLink`, the provider mutators `addTaskLink` / `removeTaskLink`, the Local Server route `task-links` and the workspace takeout. The brief's `task_links`, `taskLinks`, `addTaskLink` and `removeTaskLink` collide with all of them. **Pick: the new table is `task_items`** (bundle key `taskItems`; mutators `addTaskItem`, `removeTaskItem`, `reorderTaskItems`; Local Server route `task-items`), and the window calls them **Items**, her word. Alternative: rename the URL-links feature, which is a migration of a live table with five suites, for no gain.
2. **Only three single links exist on the cloud.** `tasks` has `asset_id` (0000, `ON DELETE CASCADE`), `scene_id` and `shot_id` (0084, same-project, `ON DELETE SET NULL`). It has **no `level_id` and no `experience_id`**: every editor sends them, and the cloud adapter's `toColumns` drops them with a warning (`TASK_COLUMNS`' comment). So today a task's level and experience exist only on the Local Server and the fixtures; on the cloud, the Timeline's and the Budget's "by level" / "by experience" groupings put every task under *No level* / *No experience*, and a level's or an experience's window lists no tasks. **Pick: no new single columns.** Items carry levels and experiences on every backend, and the provider derives each task's five single fields from its items (the first of each kind), so those groupings start working on the cloud with no change to `TimelineView.jsx` or `BudgetView.jsx`. Alternative: add `tasks.level_id` / `experience_id`, kept in step by the same trigger (it widens the old model the items replace).

Dev's data, by query on 2026-10-11: 42 tasks in 2 projects; 21 have an asset, none has a scene or a shot. The backfill makes 21 items.

### The rule every pick follows

**Items are the truth; each single field is the task's main item of its kind.** A task's items are ordered within each kind; the first asset is `asset_id`, the first scene `scene_id`, the first shot `shot_id` (and, on the Local Server and the fixtures, the first level `level_id` and the first experience `experience_id`). The database keeps the cloud's three columns in step in both directions (a trigger on `task_items`, and one on `tasks` for every writer that still writes a single column); the Local Server and the fixtures run the same rules; the provider derives the five fields from the items, so a screen never waits for the echo.
