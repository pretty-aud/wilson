3. **A trigger function shared by two tables must not name a column one of them lacks, even behind `TG_TABLE_NAME = …`.** PL/pgSQL resolves every field of an expression before it evaluates the AND, so `IF TG_TABLE_NAME = 'edits' AND NEW.shot_list_id …` raised 42703 on every `shot_lists` UPDATE. ## The API for S3b and S3c

**The three sentences S3b's walkthrough must open with** (verbatim is fine):

1. A scene or shot is ONE row shared by every shot list that contains it: renaming a shot, changing its status, notes or thumbnail in one list changes it in every list; only which scenes and shots a list holds, and their order, belong to the list.
2. The Scenes tab shows the list YOU are viewing, which can differ from the project's ACTIVE list; the Timeline, Budget, Tasks, Assets, Bins and every other surface show only the active list's scenes and shots.
3. Reviewers may now create and edit shot lists and edits (a first: they could only comment before), but they still cannot create, rename or delete a scene or shot itself; making a list active and archiving are for project managers and workspace admins only, except that whoever made a new list or edit can withdraw it again while it is untouched (on the signed-out Local Server there are no roles, so both are open).

### Mutators on `ctx` (registered in `mutationsRef` and undoable with `ctx.undo` / `ctx.redo`, except `refreshShotLists` and `clearRecentlyWithdrawn`, which is synchronous)

All refuse BEFORE any write with the backend's own wording (see "Refusals" below). All return a promise. **Membership changes are written as DELTAS** — only the rows a change names are upserted, only the ids it names are deleted — and server-first (no optimistic rollback), so a collaborator's newer items are never overwritten from this client's stale view (items are not broadcast). Adds and removals are server-first; a REORDER is applied locally first and written as positions only (a stale view never re-inserts a row a collaborator removed; on failure only the moved rows go back). A refused or conflicting membership write sets `ctx.error` and re-reads the lists (`refreshShotLists`).

### Known limits (measured in review round 2, not fixed; none reachable from S3a's UI)

- **The three backends do not agree on every malformed input.**
  - The cloud accepts a version or position sent as the string `"2"`; the Local Server and the fixtures refuse it. The provider always sends integers.
  - A partial upsert of a stored list or edit works on the Local Server and the fixtures, but fails in the cloud with 23502. The provider always sends whole rows.
  - Swapping two items' scenes in ONE upsert is accepted by the Local Server and the fixtures, but refused by the cloud (23505).
  - A stale copy of an ARCHIVED list re-sent with `archived_at: null` gets "this shot list is archived — restore it before changing it" in the cloud, but the archive-only 403 locally.
- **Local Server only:**
  - A list re-sent to ANOTHER project's URL with its old id creates a same-id copy there, because each project is its own bundle.
  - The scene cascade does not clear the cascaded shots' folder rows, their files' `shot_id` or their shot takes. The cloud's FKs do the first two; the desktop's direct shot delete never did any of the three.
- **Cloud, a database migrated mid-session.** When 0084 is applied mid-session, the client keeps stripping the 0084 columns until its next `loadProject` (a project switch or reload). A scene link typed in that window is not saved.
- **The History drawer.** Reverting a task's `scene_id` / `shot_id` to a scene that has since been deleted fails with the raw 23503.
- **`replaceShotListItems`** (adapter, route and RPC) has no caller in the app. It is the whole-set tooling / bulk-restore primitive, kept and tested on all three backends.

Added with 0086:
- **"Not Saved" is the column as it is now.** Undoing your own Save makes a list untouched again (by design), only while the stored Save is still yours (review round 2). Any list writer can still clear a snapshot through 0084's plain UPDATE policy, from a client of their own.
- **The undo of a Save checks, then writes: two requests.** A teammate's Save that lands between the re-read and the write is still overwritten, and the list then reads untouched (review round 3). Closing it needs a conditional write in each backend: on the cloud an UPDATE filtered on the stored `saved_at` (0 rows = "Saved again since"), and the same compare in the Local Server route and the fixtures. The window is one round trip while the person presses Ctrl+Z.
- **A failed re-read during the undo of a Save moves on.** The undo machinery moves a refused step to the redo stack, so a second Ctrl+Z undoes the action before it; Redo then Ctrl+Z tries the Save's undo again.
- **Title, version and summary are still last-write-wins from this client's view:** a rename re-sends the cached summary, and lists are not broadcast. A rename no longer re-sends the snapshot or an edit's items (review round 1). Before S3b adds a rename, consider a patch path that sends only the changed columns (on the cloud an UPDATE: an upsert must carry the NOT NULL title).
- **The seat is not pre-checked on a withdraw or restore.** The provider does not know the workspace role (an admin needs no seat), so a maker who lost their seat sees the optimistic change roll back, with the database's seat sentence, as with any other permission refusal.
- **A direct client write to `archived_at`** (never the app's path) still reads 0084's guard sentence, "…archived and restored only by a project manager or a workspace admin, through archive_shot_list()", which does not mention the maker. The guard was not restated for one sentence.
- **A manager's Archive of a row its maker already withdrew changes nothing** (it is already archived; `archived_by` keeps the maker), so the maker can still restore it. To settle it, the manager restores, then archives.
- **A stale second window can still add an edit to a list just withdrawn:** 0084's edits policy does not check the list, as with a list a manager archived. The maker can still restore the list.
- **A manager's own Ctrl+Z of New list is refused once someone has touched the list,** like everyone's: the provider checks "untouched" for every withdraw. Archive remains their verb.
- **The Local Server has no users,** so anyone may withdraw any untouched list or edit there (Archive is open to everyone there anyway), including the backfilled "Shot list 1" once another list is active. Drive is read-only: nothing is withdrawn there.
- **`isWithdrawn` cannot tell a withdraw from a manager archiving a list they made themselves:** there is no column, and `archived_by = created_by` in both.
- **Undo, redo and the toast's undo now run one at a time** (review round 1), so the old "two un-awaited Ctrl+Z presses push a spurious entry" limit is gone. A press while one is hanging waits behind it for at most 20 seconds from when that step started, then runs (reviews 2 and 3).
