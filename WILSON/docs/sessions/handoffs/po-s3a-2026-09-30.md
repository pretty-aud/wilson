## The API for S3b and S3c

**The three sentences S3b's walkthrough must open with** (verbatim is fine):

1. A scene or shot is ONE row shared by every shot list that contains it: renaming a shot, changing its status, notes or thumbnail in one list changes it in every list; only which scenes and shots a list holds, and their order, belong to the list.
2. The Scenes tab shows the list YOU are viewing, which can differ from the project's ACTIVE list; the Timeline, Budget, Tasks, Assets, Bins and every other surface show only the active list's scenes and shots.
3. Reviewers may now create and edit shot lists and edits (a first: they could only comment before), but they still cannot create, rename or delete a scene or shot itself; making a list active and archiving are for project managers and workspace admins only (on the signed-out Local Server there are no roles, so both are open).

### Mutators on `ctx` (every one registered in `mutationsRef`, undoable with `ctx.undo` / `ctx.redo`)

All refuse BEFORE any write with the backend's own wording (see "Refusals" below). All return a promise. **Membership changes are written as DELTAS** — only the rows a change names are upserted, only the ids it names are deleted — and server-first (no optimistic rollback), so a collaborator's newer items are never overwritten from this client's stale view (items are not broadcast). Adds and removals are server-first; a REORDER is applied locally first and written as positions only (a stale view never re-inserts a row a collaborator removed; on failure only the moved rows go back). A refused or conflicting membership write sets `ctx.error` and re-reads the lists (`refreshShotLists`).

| signature | does | undo |
|---|---|---|
| `addShotList({ title, version?, summary?, from?, fromAll?, id?, undoable? })` → row | new list; `from: listId` links the SAME scene/shot rows in the same order (D1+D3, "Save as" / "New list from the current one"); `fromAll: true` = every scene and shot in number order (for a project with no list yet); `version` defaults to `nextShotListVersion(title)`. NOT made active. One undo step. **Pass `undoable: useProjectAccess().can('project.shotlist.activate')`** — the undo archives, which only a manager/admin may. | archives the new list |
| `updateShotList(id, { title?, version?, summary? })` → row | rename / re-version / summary. Refused on an archived list. | restores the old values |
| `saveShotListSnapshot(id, { summary? })` → row | D5 "Save": writes `snapshot = { kind:'shot_list', saved_at, saved_by, title, version, scenes:[…], shots:[…], items:[…] }` — the list as it is now (field edits are already live-saved). | restores the previous snapshot/summary |
| `setActiveShotList(listId \| null)` → id | makes a list active (null clears it); refuses an archived list. Manager/admin in the cloud. | sets the previous active list back |
| `archiveShotList(listId, archived = true)` → row | archive, or restore with `false`. Refuses the ACTIVE list (D4). Manager/admin in the cloud. | the opposite call |
| `addToShotList(listId, { sceneId?, shotId?, sceneIds?, shotIds? })` → added items | adds membership; a shot whose scene the list lacks brings its scene too; already-present ids are skipped; new items go to the end of their group. | deletes exactly the items it added |
| `removeFromShotList(listId, { sceneId?, shotId?, sceneIds?, shotIds? })` → removed items | removes membership; removing a scene removes that list's items for its shots too. Nothing is deleted from the project. | re-inserts exactly the items it removed (skipping any the list holds again) |
| `reorderShotListItems(listId, orderedIds)` → items | reorders ONE group: pass scene ids (the list's scene order) or the shot ids of one scene (or item ids). Named items take positions 0..n-1; the rest of the group follows in its old order. Mixing groups throws. Only moved rows are written, positions only. | puts the old positions back |
| `refreshShotLists()` | re-reads shotLists / shotListItems / edits from the backend. | — |
| `createEditFrom({ listId, parentEditId?, title, version?, summary?, items?, id?, undoable? })` → row | new edit on any non-archived list (D6: active or not). **One linear chain per list:** `parentEditId` defaults to the chain's tip (`editChainTip(listId)`); the first edit of a list has none; a second root or a branch is refused. `items` default to the parent's (same item ids, so versions compare item by item) or `[]`; `version` defaults to `nextEditVersion(listId, title)`. Pass `undoable` as for `addShotList`. | archives the new edit |

A `listId` this client has not loaded is read first; an archived or unknown one is refused before the scene is written. **If the membership write fails, the new row is deleted again and the call throws** — under D10 a row in no list would vanish from every other tab. Undo/redo keep the membership.
- `deleteScene(id)` — deletes the scene AND ITS SHOTS on every backend (0040's CASCADE; the Local Server and the fixtures match it since review round 1); the scene and those shots leave EVERY list (archived ones too) and their tasks get `scene_id` / `shot_id = null`. **Undo restores all of it** — the scene, each shot, every membership (archived lists included), every task link. `deleteShot(id)` — the same for one shot.
- Undo primitives (registered in `mutationsRef`, not UI verbs): `putShotListItems(listId, rows)`, `dropShotListItems(listId, ids)`, `repositionShotListItems(listId, [{id, position}])`.
- The UI verbs refuse an ARCHIVED list; the database does not freeze its membership (round 2 reverted that: a delete's undo must be able to put a row back into every list it was in).

### Known limits (measured in review round 2, not fixed; none reachable from S3a's UI)

- **The three backends do not agree on every malformed input.**
  - The cloud accepts a version or position sent as the string `"2"`; the Local Server and the fixtures refuse it. The provider always sends integers.
  - A partial upsert of a stored list or edit works on the Local Server and the fixtures, but fails in the cloud with 23502. The provider always sends whole rows.
  - Swapping two items' scenes in ONE upsert is accepted by the Local Server and the fixtures, but refused by the cloud (23505).
  - A stale copy of an ARCHIVED list re-sent with `archived_at: null` gets "this shot list is archived — restore it before changing it" in the cloud, but the archive-only 403 locally.
- **Local Server only:**
  - A list re-sent to ANOTHER project's URL with its old id creates a same-id copy there, because each project is its own bundle.
  - The scene cascade does not clear the cascaded shots' folder rows, their files' `shot_id` or their shot takes. The cloud's FKs do the first two; the desktop's direct shot delete never did any of the three.
- **Cloud, a database migrated mid-session.** When 0084 is applied mid-session, the client keeps stripping the 0084 columns until its next `loadProject` (a project switch or reload). A scene link typed in that window is not saved.
- **The History drawer.** Reverting a task's `scene_id` / `shot_id` to a scene that has since been deleted fails with the raw 23503.
- **Undo, pre-existing.** Two un-awaited Ctrl+Z presses can push a spurious entry. This is the provider's undo machinery, before S3a.
- **`replaceShotListItems`** (adapter, route and RPC) has no caller in the app. It is the whole-set tooling / bulk-restore primitive, kept and tested on all three backends.
