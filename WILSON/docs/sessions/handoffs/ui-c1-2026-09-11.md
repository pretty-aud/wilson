## 5. Traps hit

### 1. 🚨 A GREEN LOCAL VITEST RUN DOES NOT MEAN THE VITEST JOB IS GREEN

The Vitest job has **no `.env.local`**. A render test mounts a real component,
so it pulls in that component's whole import graph, and somewhere down it sits
`src/cloud/auth/supabaseClient`, which calls `createClient` **at module load**
and throws `supabaseUrl is required.` when the env vars are absent. The whole
test FILE then fails to import, and the error says nothing about the test.

Every local run was green. CI went red on the integration merge.

`pages.test.js` hit the same wall in `720affb`. The fix is two lines:

```js
vi.mock('../../cloud/auth/supabaseClient', () => ({
  supabase: {},
  hydrateSupabase: async () => {},
}))
```

**Every later lane will hit this the moment it writes its first render test,
which is every lane.** Check your run the way CI runs it:

```bash
mv .env.local .env.local.bak && npx vitest run ; mv .env.local.bak .env.local
```

### 2. 🚨 THE BROWSER PANE'S DEV SERVER SERVES THE CANONICAL CHECKOUT, NOT YOUR WORKTREE

`preview_start` resolves `.claude/launch.json` from
`C:\Users\Audrey\Documents\My_Work\Dev_Work\wilson\WILSON`, not from the
worktree, and runs the dev server there. It starts, it serves, the app looks
fine — and **none of your changes are in it**, because it is serving a
different branch's files. A `launch.json` written inside the worktree is not
even found ("No server named … Available servers: …" lists the canonical
file's entries).

It cost about twenty minutes and two wrong theories (a missing env var, then a
stale Vite cache) before the obvious check found it:

```bash
curl -s http://localhost:PORT/src/components/<your file> | grep -c <a string only you wrote>
```

Zero means you are looking at someone else's tree. Do that check **first**,
before trusting anything you see in the pane.

The way through is to run Vite yourself from the worktree and open the pane at
its URL:

```bash
npx vite --port 5207 --strictPort      # run_in_background, from the worktree's WILSON/
```

then `preview_start` with `{url: "http://localhost:5207"}`. `VITE_DEV_AUTOLOGIN=tester`
only reaches the app on a server started this way.

### 3. The extraction commit caught its own defect on the first file

`ProjectDetailPanel`'s `L.select` carried `color` in the inline style object,
so the extracted `.pd-select[data-empty]` rule could never have won. `color`
had to leave the style object for the rule to matter. This is exactly the
failure plan §1 and review Risk 4 describe, met while doing the step that
exists to prevent it. **Do not assume the extraction is mechanical**: after
moving a branch to CSS, grep the file for the property you just moved.

### 4. The action columns were narrower than the buttons in them

`table-layout: fixed` keeps a percentage exactly, and both tables inherited an
action column at 4 percent. At the 1280px minimum window that is a **38px**
cell on the rate card holding two 28px icon buttons plus a 24px inset — they
need 82px. Projects had the same defect one button smaller.

Nothing about this is visible in a screenshot of an empty page, and no test
caught it. It was found by building a probe of the real stylesheet in the
running app and measuring `scrollWidth` against `clientWidth` for every cell:

```js
[...host.querySelectorAll('tbody td')].map(td => ({ need: …scrollWidth, have: td.clientWidth }))
```

**Every session that declares percentage column widths should do this once**,
at 1280, before claiming the table is done. Widths summing to 100 is necessary
and not sufficient.

### 5. `Tabs` is 36px and the Toolbar's contract is 28px

See the kit requests below. The symptom is a toolbar that renders 53px instead
of 44px with one child standing proud of the rest.

### 6. The kit's `Table` has no footer slot

The per-currency totals rows are the last rows of the `<tbody>` rather than a
`<tfoot>`. Correct HTML, right picture, wrong element. Kit request below.

### 7. 🚨 A FIX IS NOT DONE WHEN IT IS WRITTEN — three of this session's defects were introduced by a correction to an earlier one

The most useful line in this file, because it is about process rather than
about this code.

- Round 1 found the %/$ toggle made a 63px row. The correction put the cell on
  one line, which crushed the EDITABLE value to **three pixels** while the
  read-only figure it derives from survived.
- That correction's correction made the cell a grid — and left the derived
  amount OUTSIDE the grid, so all three of its new declarations were no-ops on
  an inline span and the figure truncated exactly as before. **The test written
  to catch this read the declarations out of the stylesheet and passed.** Three
  attempts at one cell.
- Round 1 found the tree indent lying. The correction made tree order the
  default, which left the Name header claiming `aria-sort="ascending"` over
  rows that were not in name order, and removed flat A-to-Z as a reachable
  state. The third answer dropped the indent instead.
- Round 1 split "Dates" into a `Field` per control. That broke the
  `.ui-field + .ui-field` adjacency on ONE side of a two-column form, so the

The plan already says this — "R2 attacks R1's corrections (an R1 fix has been
an inert guard before)" — and it is exactly right. **Measure the fix, in the
browser, on the shipped markup.** A test that reads a stylesheet proves a
declaration exists, not that anything is shaped by it; jsdom applies no CSS;
and a screenshot of an empty table shows neither. The probe in trap 4 is the
tool, and it found every one of the above.

## 9. Kit requests (plan §4 / C8 — `src/ui/` and `src/index.css` are Foundation's)

Five, all real, all found by USING the kit rather than by reading it, and two
of them found only by measuring what it rendered. Each is scoped locally in
`resources.css` so these three pages are correct now; each belongs in
`index.css` so every page gets it. Three of the five affect Team Members
today.

1. **`Toolbar` does not hold `.ui-tab` to the 28px control height.**
   `index.css` enforces the Toolbar's one-baseline contract for `.ui-btn`,
   `.ui-iconbtn`, `.ui-input` and `.ui-chip` — but `.ui-tab` is
   `--control-md` (36px), so a tab inside a toolbar stands 8px proud and takes
   the row from 44px to 53px. **Team Members hits this too** the moment an
   admin sees more than one saved view; it does not show in tester mode, which
   is why F2 did not see it. Add `.ui-tab` to that rule.
   Local scope: `.rs-page .ui-toolbar .ui-tab { height: var(--control-sm); }`.

2. **`Tabs` items cannot carry a `title`.** They take `disabled` and `count`.
   The Rate card's Internal tab is `disabled` when its card does not exist, and
   it carried a `title` explaining WHY — Audrey's own complaint ("when i press
   internal i am not seeing the internal one"). Rather than lose the
   explanation to a tooltip the kit cannot render, the page now says it in a
   `Banner` in the flow. A `title` on an item would be two lines.

3. **`Table` has no footer slot.** The rate card's per-currency totals are the
   last rows of the `<tbody>`. A real `<tfoot>` would stay put under a
   scrolling body and be announced as the summary it is. Suggested: a `foot`
   prop rendered into `<tfoot>`, mirroring `head`.

4. **`.ui-field + .ui-field { margin-top: 16px }` fires on a HORIZONTAL pair.**
   It is a vertical-stack rule expressed as a sibling rule, so two fields
   side by side in a grid or flex row get 16px of top margin on the second
   one — measured, that put "End" 16px below "Start" and stretched "Start" to
   cover the gap, so neither edge lined up. It wants to be a stack rule (a
   `Field` group component, or `:where()`-scoped to a column). **Team
   Members' `.tm-rate-pair` is a horizontal pair too and carries the same
   16px.** Local scope:
   `.pj-pair > .ui-field + .ui-field { margin-top: 0; }`.

5. **`Select` renders its native dropdown chrome LIGHT on the dark ground.**
   `color-scheme` is `normal` everywhere (grepped: the string appears nowhere
   in `index.css`), so the platform paints the select's own button area light —
   a near-white region on a dark page, which is C9's shape arriving through the
   UA stylesheet rather than through a rule. **This is app-wide, not this
   session's**: Team Members shows it identically, and it was left alone for
   that reason. One line: `color-scheme: dark` on `[data-surface="dark"]` (and
   `light` on `[data-surface="light"]`), with a contrast note. **This session
   scoped it locally** as `.rs-page .ui-input { color-scheme: dark }` — it
   also fixes the date picker's calendar glyph, which `ProjectDetailPanel`
   used to set inline and lost in the move to the kit `Input` — and verified
   in the running app that the project select's chrome and the date field both
   go dark with it. Every other dark page still has the light version.
