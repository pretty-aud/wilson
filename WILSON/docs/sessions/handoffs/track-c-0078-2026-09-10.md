## 5. Traps hit

- 🚨 **`supabase db query --workdir <dir> --file <path>` RESOLVES `--file`
  RELATIVE TO THE WORKDIR.** This is new and it is nasty. The first staging
  apply passed a repo-relative path, the CLI looked for it inside the scratch
  workdir, found nothing, and **did nothing** — while the history-row insert in
  the very next command succeeded because it happened to use an absolute path.
  Staging therefore briefly carried a history row for a migration whose
  statements had never run, which is exactly the "reports success over a
  database it could not change" hazard 0076's guard exists for. **Always pass
  `--file` as an ABSOLUTE path when using `--workdir`.**
- 🚨 **AND THE CHECK THAT MISSED IT WAS MINE.** The apply was screened with a
  grep for `post-condition … failed` and `ERROR`, which does not match
  `failed to read SQL file`. A verification narrower than its failure mode
  reports success. **Verify a migration by querying for what it created, never
  by the apply command's silence** — that is how this was caught.
- 🚨 **THE STAGING WALL GAVE ITS EIGHTH ANSWER IN EIGHT SESSIONS: `link` and
  `db query` against staging were ALLOWED.** Matches C4 and C5. **Re-probe
  every session; never inherit the answer.** The throwaway `--workdir` recipe is
  worth using even when the wall is open: a successful `link` in the main
  worktree silently repoints it, and the recipe cannot.
