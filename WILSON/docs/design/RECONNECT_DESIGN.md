## 2. The detection — unchanged, with one scale

`src/cloud/connectionWatchdog.js` as it stands: the one fetch supabase-js uses, the 20 s budget, the scope (every `/auth/v1/`, every `/rest/v1/`, `GET`/`HEAD` of `/storage/v1/object`), `navigator.onLine` true, the ticker only while something is pending. A healthy round trip is hundreds of milliseconds, the auth screens' own ceilings are 15 s, and 20 s is still inside the time a person stays looking at a screen. **One addition (round 1, F5):** a request with a body gets one second more per whole 50 KB of it, counted in bytes (a body under 50 KB adds nothing; a 1 MB course save: 40 s), so a slow uplink is not read as a dead one — nothing changes for the body-less reads, the token refresh and the small writes that are nearly all of the traffic (round 2, F6).

## 3. The recovery — (a), the abort, chosen by the measurement

**At the budget the watchdog aborts the request instead of only counting it.** Every watched request gets its own `AbortController` (joined to the caller's `signal` when one is passed, as supabase-js's `.abortSignal()` does; a caller's own abort is a settle, never a loss); when a request has been pending for its budget while the browser says it is online, the watchdog aborts it. Then, measured:

- the SDK's refresh rejects, the SDK retries by itself (one more attempt at 20.2 s), keeps the session, and keeps knocking: every queued caller's turn is a new attempt — on the wire, one attempt per budget;
- when the network answers, the next attempt lands, `TOKEN_REFRESHED` fires, every caller still queued completes, and the app continues with the same client, the same channels, the same `sharedAuthedClient` — no reload;
- a PostgREST or storage request that hangs on its own (the token fine) is aborted the same way: its caller's error path runs at 20 s instead of never.

**Why not (b), a fresh client built on detection.** It works mechanically (fact 3) and buys nothing (a) does not: the fresh client's own first refresh hangs on the same dead network, and the old client's waiters stay held unless something aborts them, which is (a). Its cost is real: 32 files import the module-level `supabase` (R.A.B.B.I.T.'s `sharedAuthedClient` is the same instance, `RabbitProvider` subscribes to its auth events, two realtime channel sites, `usePermissions`, the pet's user state), every one of which would have to re-bind.

**Why not (c), an SDK option.** `lockAcquireTimeout` governs the lock function, which is a no-op here, and is never consulted on the queued branch (fact 2); a custom `lock` with a timeout would run a second refresh beside the hung one, sharing the same `refreshingDeferred`, which is the same pin.

**What the SDK gives us that this design does not re-do:** the retry. No module re-issues the refresh; the measured loop does it. The one call the app makes is the nudge below.

### What `lost` means, and when it clears

Today a watched request that settles late clears the banner. With aborts, nothing settles late: an aborted request is a settle, and it must not clear the condition, or the strip would blink at the budget and vanish with the app still stuck. And a clear must come from the service that hung: GoTrue stuck while PostgREST answers is an ordinary partial outage, and a PostgREST answer says nothing about it (round 1, F1). So:

- `lost` is kept **per family** — `auth` (`/auth/v1/`), `rest` (`/rest/v1/`), `storage` — turns on for a family at its first abort, and **clears for that family only when a real request of that family resolves with a status under 500** (an answer is a connection; a 5xx from the gateway, a rejection, an abort are not; nor is an answer that lands after the request was aborted — the abort is what raised the loss, round 2 F9). The strip shows while any family is lost; its clock runs from the first raise and is not restarted by a later abort, of that family or another;
- while a family is lost the watchdog **pings** it every 10 s with a 5 s budget: `GET <origin>/auth/v1/health` for auth, `HEAD <origin>/rest/v1/` for rest, `HEAD` of the hung object's own address for storage — each with the `apikey` header of the request that hung (both read from that request; no new seam in the client module). An aborted ping changes nothing. **What an answered ping proves decides what it does** (round 2, F2): the storage ping repeats the hung request itself, so it clears; the auth and rest pings answer from the gateway and the schema cache even while the database behind them is stuck, so they clear nothing — they tell the client module, which asks for real: for auth `supabase.auth.getSession()` (the SDK's refresh, now rather than at the ticker's next tick; queued behind the attempt in flight if the lock is held), for rest a `HEAD` of one `workspaces` row — and that real answer clears. Otherwise a stalled database read as a recovery every ten seconds: the strip flickering, re-announced, and never reaching the reload words (measured by round 2 on the build as it first stood). CI's Playwright scenario 11 holds every `/rest/v1/` request open and expects the strip to stay, which it does: the rest ping and the one-row HEAD both hang;
- **an answered ping aborts, at once, every request of that family that was already pending when the ping was sent** (round 1, F3; never one sent after it): after a sleep-wake or a VPN reset the old connection is dead and would otherwise sit until its own budget; aborting it makes the SDK's next attempt — which lands, and clears — the next thing on the wire. So the time from the network returning to the refresh landing is the ping cadence plus a round trip, about 11 s at most (measured on the final code: 6.2 s);
- **a sign-out made during a hang stays a sign-out** (round 2, F1). App's `signOutLocal` and the operator console's `handleSignOut` clear the stored session and then call the SDK's `signOut`, which queues behind the hung refresh; before S1 that queue never drained and the strip's Reload threw the page away. Now the queue drains and the SDK's `signOut` runs on the still-dead network: its logout is aborted, the SDK keeps the session (a retryable error removes nothing), its ticker goes on refreshing it, and the `TOKEN_REFRESHED` that lands when the network returns would have written the ended session back into storage. So both sign-outs call the client module's `endSessionLocally()` right after clearing the store: while that latch is set a refreshed token is not saved, the guard reads the person as signed out, and the auth retry above finishes the sign-out (`signOut({ scope: 'local' })`) instead of asking for the session; the sign-out landing (`SIGNED_OUT`) or a new sign-in clears it.

### The holder's read, and the guard (round 1, F2a)

By fact 2 the first caller — the one whose `getSession()` started the hung refresh — returns the result of its own loop even when a later attempt succeeded: `{ session: null, error }`. supabase-js then drops the error and sends that caller's request with the **anon key** (fact 6: measured, 401 on `workspaces`; on a table anon may read, an empty 200 that looks like data). So the client module's fetch refuses, before the watchdog ever sees it, **a `/rest/v1/` or `/storage/v1/` request that carries the anon bearer while a person is signed in** (signed in: the last auth event carried a session; signed out: `SIGNED_OUT`). The refusal is a rejected fetch with one sentence ("Signed in, but the session check failed; the request was not sent"), which postgrest-js turns into the caller's error result (status 0) — the caller's own error path, never an empty success. Nothing legitimate is lost: every PostgREST and storage call the app makes while signed in carries the session's token; the anon calls (`resolve-login`, the Edge Functions) are raw fetches outside the client.

### Thresholds (mine to pick, picked)

| Number | Value | Why |
|---|---|---|
| Budget | 20 s, plus 1 s per 50 KB of body | unchanged for everything but a large write (§2) |
| Ping cadence, budget | 10 s, 5 s | a healthy `HEAD` or `GET /health` is under a second; six tiny requests a minute per lost family while lost, nothing otherwise; the SDK's own attempts are one per budget on top |
| The words change | 60 s lost — 80 s into the hang | three pings and two SDK attempts without an answer; after that the strip says reload, and the pings continue so a late answer still clears it |

## 5. What is never retried, and what an abort costs

- **Outside the watchdog by construction, and staying so:** uploads (`POST`/`PUT /storage/v1/object`), the resumable path, every Edge Function call (raw fetch, a 150 s wall clock), realtime (a websocket). Never watched, never aborted, never pinged.
- **A write aborted at 20 s may have landed** — an insert, an update, an auth write (`PUT /auth/v1/user`, an MFA enrolment). The caller's error path runs ("could not save") while the row may exist. No caller retries a write on an error by itself (grep: no retry loop around any `.insert`, `.update`, `.upsert` or `.rpc`); the person's own retry of a **create** can duplicate it, because R.A.B.B.I.T.'s ids are the server's (an update or a delete repeated is the same row). Today the same write hangs for ever, the person reloads, and the same duplicate is one click away. Not worse; sooner, and the list reloads with the row in it.
- **A refresh aborted after GoTrue rotated the token** (the request arrived, the answer was lost). Every attempt is another presentation of the old refresh token: accepted inside GoTrue's reuse interval (10 s by default), refused after it, and a refusal removes the session — the sign-in screen, unprompted, with whatever was unsaved. Today the same loss follows the person's own reload, a few seconds later, since the stored session holds the same old token. The same loss, sooner (round 1, F7). Not measurable without a real session, which this session never has (§6).
- **Two clients, one refresh token** (round 1, F8): two web tabs of `/wilson` hydrate the same stored session, and each rotates it on its own — a hazard of `persistSession: false` that predates this design and is not changed by it; the desktop has one renderer; the operator console has its own token under its own key.
- **The auth screens' own ceilings (15 s, `withTimeout`) are under the budget**, so a sign-in or MFA verify is already abandoned by its screen before the watchdog aborts it; their reasoning about a request that "may have taken effect server-side" is unchanged.
- **A queued caller still waits** while the network is dead (fact 6). The design does not fail them: the alternative is a non-retryable error, which makes the SDK drop the session and sign the person out — worse than a reload. The strip says what is true meanwhile.

In all six the SDK holds no session afterwards and its queue is empty, and **nothing touched the stored session**: the app keeps the saved tokens whatever the outcome. **The desktop app, the same code** (a development-mode build, Electron 33, a scratch userData, a made-up session saved through the preload bridge): with `WILSON_DEV_OFFLINE=1` the sign-in screen is up **4.4 s** after the page loads; with `=stall` **19.3 s** after, and S1's strip ("Connection lost — reconnecting…") joins it on the sign-in screen within the next 25 s. Her timings of 2026-09-10 are the control and agree (4.5 s; 15.0 s plus 4.3 s); the 4.3–4.5 s is the sign-in screen's own entrance. What the table adds: an expired token's restore keeps the SDK's queue held for 25–40 s after the screen has given up (G3, G4), and a stalled launch raises S1's strip on the sign-in screen. **The token's lifetime** (the brief: measure it, do not assume 3,600 s): the one read that measures it on wilson-dev, the spacing of a session's refreshes in `auth.refresh_tokens`, aggregated with no token selected, was refused by the permission classifier ("Production Reads"); the repo says 3,600 s (`supabase/config.toml` `jwt_expiry`; handbook §4.3). Nothing below depends on it: with an hour's token inside a four-hour cap both paths, unexpired and expired, are ordinary, and both are designed.

**The desktop keeps nothing in localStorage across a relaunch** (measured the same day, the same build): the window loads `http://127.0.0.1:<port>` and the port is the local server's `listen(0)` (`startLocalServer`, `electron/main.cjs`), new at every launch, so every launch is a new origin: a key and a cap record written at one launch were absent at the next (ports 53343, then 53359). So on the desktop the cap's `start()` never finds its record at launch and hands every launch a fresh four hours: today the absolute cap runs from the latest desktop launch, not from the sign-in (OUTSTANDING S2-01; the cap is not this brief's to change). §11.3 is written for it.

### 11.2 Which failures open the shell, and what a refusal does to the stored tokens

The shell opens offline only when the saved sign-in is inside the cap (§11.3) **and** the auth server could not be reached:

- **Reached nothing:** the launch's health probe not answered by GoTrue (§11.4: no answer within 5 s, a rejected fetch, a 5xx, or an answer that is not a JSON object, which is what a captive portal's page or a proxy's error page is); then, from `setSession`, auth-js's `AuthRetryableFetchError` (status 0: rejected, aborted, or not GoTrue's JSON; or 502, 503, 504), an `AuthApiError` of 500 or more, an `AuthUnknownError` (an error answer that is not GoTrue's), and the launch ceiling (10 s).
- **A refusal:** every other answer from GoTrue: 400 (an invalid or spent refresh token: G6), 401, 403 (G5, `bad_jwt`), 404, 429, and `session_not_found` (`AuthSessionMissingError`; the SDK emits `SIGNED_OUT`). The launch goes to the sign-in screen, as today.

**The stored tokens after a refusal, inside the cap.** Today nothing clears them (G5, G6). After S2 a refusal that ends the session (400, 401, 403, `AuthSessionMissingError`, `AuthInvalidJwtError`) at a launch inside the cap clears the stored session **if it still holds the refresh token that was refused**: another tab of `/wilson` may have saved a newer one since this launch read it (the desktop has one renderer). A refused sign-in is not a saved sign-in, and kept, it would open the shell at a later offline launch inside the cap. Any other refusal (a 404, a 429) keeps them, as today; a launch that reached nothing never touches the store; outside the cap the restore is today's and keeps them too (a launch outside the cap never opens offline, so nothing is gained there). **The one blind spot:** a portal that answers GoTrue's health probe with a JSON object and then answers the refresh with a JSON 200 holding no session would read as `AuthSessionMissingError`, a refusal, and clear the store. Portals answer HTML; it is stated, not designed against.

### 11.3 The four-hour test: the earlier of the cap's own record and the token's own sign-in time

`sessionTimeouts.js` keeps one record per surface, `<surfaceKey>.start = { sid, at }`, keyed by `sessionIdOf(session)` (the JWT's `session_id`, kept across refreshes), and ends a session when `now - at >= capMs` (`evaluate()`); a resumed session keeps its original start (`start()`). On the web that record is written seconds after the sign-in and found at every later launch. On the desktop it is never found at launch (§11.1: a new origin each time), so a test on the record alone would call every desktop launch outside, and the shell could never open offline where an offline launch matters most. So the start the launch tests is **the earlier of the two starts this computer can prove**: the cap's own record (read as `start()` reads it: this session's id, a finite `at` not in the future), and **the token's own sign-in time**, the earliest timestamp in its `amr` claim (GoTrue stamps every access token of a session with the methods used to sign in and when, `[{ method: 'password', timestamp }]`, and keeps them across refreshes because they are the session's claims; the app's access-token hook starts from GoTrue's claims and adds only `app_metadata`, `0003_fix_access_token_hook.sql`); a timestamp in the future proves nothing, as a record in the future does not (a clock behind the server's). Inside means `now - start < capMs`, with `capMs` the cap's own (the dev-only override `sessionTimeouts.js` honours is honoured here too, so the cap can still be shrunk on a dev server). Neither start known (a token without `amr`, which GoTrue does not issue for a password sign-in, on a computer with no record) is outside: the sign-in screen, as today.

Two read-only exports of the same file do it, `sessionStartOf(session, { storage, now })` and `insideSessionCap(session, { storage, now })`; no rule there changes. **Offline is stricter than online, never more lenient:** the earlier start is never later than the record `start()` resumes, so the cap's first evaluation, milliseconds after the shell opens, cannot find a session younger than the launch did; a session with no record (the desktop, every time) or a record in the future gets a fresh four hours from `start()` online and the sign-in screen offline unless its `amr` proves it young. A launch inside the last seconds of the four hours opens, and the cap ends it at `start()` with its notice, as an online launch at that age does. The tests pin these shapes, not an equivalence.

### 11.4 The launch, step by step (`hydrateSupabase` on the app surface)

The hold is the app surface's alone: App's `checkSessionValid` calls `hydrateSupabase(saved, { holdOffline: true })`; the operator console (`OperatorApp.jsx`, which also restores through `hydrateSupabase`) passes nothing and keeps today's restore exactly (round 1, F1).

1. No tokens: no session, as today.
2. Without `holdOffline`, or outside the cap: today's restore, untouched. `setSession`, bounded at 15 s by `checkSessionValid`; any failure is "no session"; no probe, nothing cleared. Online, a session past the cap restores and the cap ends it at once with its notice, as today.
3. Inside the cap: first **`GET /auth/v1/health`** with the anon key and **the launch budget, 5 s**, through the watchdog's `launchProbe` (the base fetch, outside the wrapper's table, so it raises nothing and tells no listener). It counts as answered only when it is a 200 whose body is a JSON object, GoTrue's own health answer. Not answered: **hold**, and no real request is ever sent, so the SDK's retry loop never starts and nothing queues (G1–G4 at once or at 5 s, `navigator.onLine` false included: the probe fails in a millisecond there, round 1, F7).
4. Answered: `setSession(saved)` with S1's budgets (20 s; no shorter budget on a real request: a slow but live auth server must not be cut off, and a refresh cut off after GoTrue rotated the token would be refused at its retry: round 1, F2), raced against the **launch ceiling, 10 s from the start of step 3**. A session: the shell, online, as today. Reached nothing (§11.2) or the ceiling: **hold**. A refusal: no session, the store cleared as §11.2 says.
5. **A late answer.** When the ceiling decided, `setSession` goes on in the SDK; its result, whenever it comes, is handled: a session ends the hold (the confirmation, §11.5), a refusal ends it as the way back's refusal does (§11.5), anything else changes nothing. A session that lands before the hold is set is the same confirmation.

`checkSessionValid`'s 15 s bound stays where it is (pinned), and inside the cap it is never reached: the decision takes at most the 10 s ceiling. The decision itself is one exported function of `connectionWatchdog.js`, `restoreSavedSession({ auth, saved, insideCap, probe, ceilingMs })`, so the probe runs the code the app runs; `hydrateSupabase` gives it the app's client, the cap answer and the watchdog's probe, and acts on its outcome (`online`, `held`, `refused`, `none`).

**Hold** means: the client module keeps `saved` as the held session, latches `signedIn` (§11.5), tells the watchdog the launch reached nothing (`launchedOffline`, §11.6), and returns `saved`, so `checkSessionValid` hands the mount effect a session exactly as it hands a restored one, and `authed`, the session id and the shell follow unchanged. The id is the saved token's `session_id`, so the cap's clock resumes where it can (the web) and the idle clock starts as at any launch.

### 11.5 Holding a session the SDK does not

`_setSession` saved nothing (G1–G4), so for as long as the hold lasts:

- **The guard is latched from launch.** `signedIn` is set when the session is held, not by an auth event (none fires). supabase-js then sends every PostgREST and storage request with the anon bearer (`getSession()` returns null at once: nothing queues, nothing is pending), and the guard refuses each one before the network, with its reason while held: *"Could not reach the database, so the request was not sent."* (status 0): the caller's own error path, never an empty success, never the anon key on the wire. A `SIGNED_OUT` while a session is held (the SDK's, inside a refused restore or re-hydration) leaves the latch on; the hold's end turns it off. Edge Function calls (raw fetch) carry no session token and fail at the network.
- **`usePermissions` reads the held token's claims, with no network read:** `userId` (`sub`), `workspaceId` (`app_metadata.workspace_id`), `workspaceIds`, the role and the operator flag, exactly as `snapshot()` reads a live session's. Its rule becomes *the SDK's session if it has one, else the held one*, recomputed on every auth event and every change of the hold, so an `INITIAL_SESSION` with no session arriving after the hold cannot empty it; a new field, `offline`, is true while the claims come from a held session. **`ready`** means what it means online, the first session read resolved, and it is also set when the hold is (round 1, F11). So a company member stays one offline (`cloudMode` is only `app_metadata.workspace_id`), the pet keeps its owner, and the "solo-user rules" of OUTSTANDING's fix shape become **the person's own role, from the saved token**: an admin may still change this computer's storage folder and a member may not (`canEditMachineRoot`); only a token with no workspace keeps a solo user's control. The fix shape as written would have handed every company member that control while offline.
- **The re-hydration.** The hold marks the auth family lost (§11.6), so the watchdog pings `GET /auth/v1/health` every 10 s, and at once on the window's `online` event. The first answered ping reaches the client module (`onPingAnswered('auth')`, S1's seam), which, while a session is held, calls `setSession(held)` (one at a time, and with the auth pings quiet until it settles, so the next ping's answer cannot abort its request: round 1, F8) instead of asking for the session. An unexpired token is checked with `GET /user` and the SDK emits `SIGNED_IN`; an expired one is refreshed, `TOKEN_REFRESHED`, and the existing hook saves it. Either event, or `setSession`'s own result, ends the hold (the SDK holds the session now): **the confirmation**. That request's answer clears the auth family, so the strip goes. R.A.B.B.I.T. re-lists on the event as it does today (`RabbitProvider`'s listener: `status()`, then `listProjects()`), and `usePermissions().offline` turns false, which the other screens and the once-per-sign-in reads key on (§11.9). Reached nothing again: still held, and the next answered ping tries again. **A refusal on the way back:** the hold ends, the store is cleared as §11.2 says, and App ends the session through `signOutLocal({ event: null, notice })` (no `auth_events` row: there is no token left to write one with; `notice` is the one new parameter, because `describeSessionExpiry` knows only the cap's and the idle timeout's words), so the person lands on the sign-in screen with one line: *"Signed out: your saved sign-in was not accepted when the connection returned. Sign in again to continue."*
- **What the queued callers do meanwhile: nothing queues.** With no session in the SDK, `getSession()` answers at once, so a read is refused by the guard at once rather than held, and a screen's own retry is refused the same way until the confirmation. During the re-hydration the SDK's queue is held for its request, and a caller arriving then gets the session. The one exception is a partial outage, GoTrue answering `/health` while its user or token endpoint stalls (step 4 or a re-hydration): the SDK's queue is then held for that request's budget, 20 s, which is S1's case, with the strip up.
- **A sign-out while held** (the Settings button, the idle timeout, the cap): `endSessionLocally()` also ends the hold, so the guard, `usePermissions` and the pet follow the sign-out at once, and the launch's loss is lowered (§11.6, `launchEnded`). **A sign-out during a re-hydration:** the re-hydration's result is dropped: the `SIGNED_IN` its `setSession` emits does not clear the sign-out latch, and the session it gave the SDK is signed out locally, so a person who signed out is never signed back in by a request they did not see (the shape of S1's round 2, F1). **The sign-out of a held session** writes no row (no `auth_events`, no WIL-1002: the SDK holds no session, so there is no token to write one with), releases no AI files and queues no SDK sign-out, which would wait behind auth-js's lock and run on whatever session it holds by then; every piece of held work still out is aborted, and its later attempts are answered without the network (build review round 2, F1 and F4, §11.18).

### 11.6 The watchdog's launch path (none of S1's budgets moves)

- **`launchProbe({ origin, apikey })`:** the health request of §11.4 step 3, sent with the base fetch and aborted at the launch budget, 5 s; it resolves whether GoTrue answered. Outside the wrapper's table, so it raises no loss and fires no listener; the only new budget, and it is on a request the launch adds, never on one the SDK sends.
- **`launchedOffline({ origin, apikey })`:** the hold tells the watchdog the auth family is lost from now, and where its ping goes (the client module's URL and anon key: at a launch that sent nothing, no request has been seen to remember them from). The strip is therefore up from the first paint of the shell, whether or not the browser says online; S1's watchdog raises only on an abort and aborts only while `navigator.onLine` is true, so a real offline never showed the strip. **A loss the launch raised is pinged whether or not the browser says online** (instead of waiting for the `online` event alone: a virtual adapter can leave `navigator.onLine` false on a working network; a ping on a dead one fails in a millisecond: round 1, F7). Aborts of real requests still happen only while it says online, with one exception: while a loss the launch raised is up, a real auth request (the held work's own: everything else waits behind it in the SDK's lock) is cut at S1's budget whatever the browser says, since `quietWhile` keeps away the pings that would otherwise end a stall (build review round 2, F3).
- **"Reconnecting" throughout on a launch that was never online.** Until a family the launch raised has answered once, the phase stays `reconnecting` however long the loss lasts; it never turns to `reload` at 60 s, because a reload would only launch offline again (her ruling: *the strip says reconnecting throughout*). After the first answer S1's rules apply unchanged.
- **`launchEnded()`:** when the hold ends without an answer (a sign-out while held) or by a confirmation whose request answered before the loss was raised, the loss the launch raised is lowered, unless a real auth request is pending: otherwise the strip would stay on the sign-in screen for ever on a working network, since with no session there is nothing real left to ask (round 1, F3).
- **`quietWhile('auth', promise)`:** while the re-hydration (or the launch's late restore) is out, no auth ping is sent and no auth answer clears the strip: that work decides (build review round 1, F2, §11.17).

### 12.2 The cap: at a restore, `start()` takes the start the offline launch tests

**The rule.** At a restore (App's start-up check, `checkSessionValid`: every desktop launch, every web reload; the operator console's boot) `start()` resumes the earlier of the two starts this computer can prove, read as §11.3's offline test reads them and through the same two readers: the cap's record (this session's id, a finite `at` not in the future) and the token's own sign-in time (its earliest `amr` timestamp, applied only when it is not in the future by `start()`'s own clock). Neither known: now, as today. No record found: it writes one holding that start. **A fresh sign-in passes no time** (App's `handleAuth`, the console's `handleSignedIn`): its record is the moment of the sign-in, as today (round 1, F4: there the token's time adds only the clock's skew, and a computer four hours or more ahead of the server would be signed out at every sign-in). The surfaces hand the hook the raw earliest `amr` (it does not change within a session) through one read-only export beside `sessionStartOf`; the hook restarts on the same three things as today (`enabled`, the session id, the surface key: a new sign-in is a new id), so a token refresh restarts nothing; `evaluate()`, `expire()`, the numbers and the surface keys do not change.

**Why this, and not the record kept by the main process.** It is one rule in one function, with no new storage and no new channel; at a restore it is the start the offline launch already tests, so an online launch and an offline one cannot disagree about a session's age; and it holds whatever happens to the renderer's storage: the first launch after this update (the record sits in the last launch's origin), a lost or refused storage file, the settings' path put to her instead of built. Kept by the main process, the record would need a synchronous channel or a seeded copy, which is §12.5's machinery; with §12.5 built the desktop finds its record as the web does, and the token's time is the floor under it.

**Never more lenient, on either build.** The earlier of two starts is never later than the record alone; on the desktop today's start is the launch itself, and no proven sign-in time is later than now. On the web the change is the seconds between the sign-in and its first `start()` (the record is written there, the token's time is the sign-in itself), counted from the first reload, plus a clock that runs ahead of the server's: `amr` is the server's clock read against this computer's, so a computer X ahead ends its four hours X early after a reload or a relaunch, and one four hours or more ahead is signed out at every reload or relaunch (never at the sign-in itself). A computer X behind reads the token's time as in the future for X after the sign-in, where it proves nothing and the record (or now) decides, as today. A skewed clock only ever ends a session early.

**What the person sees.** A relaunch inside the four hours keeps the sign-in's deadline: the five-minute notice comes at four hours less five minutes from the sign-in, not from the launch. A relaunch past it ends the session the moment the shell opens (`start()` ends in `evaluate()`: `session_cap`, its `auth_events` row and the sign-in screen's line), as a reload past it does on the web; offline, S2's launch never opens it (§11.3).

**The pins that move.** `sessionTimeouts.test.js`'s CONTROL (*with no record start() hands out a fresh four hours, while the launch refuses an old amr*) pins today's gap, and as written it would stay green (its `make()` passes no time: round 1, F5): it is rewritten to pass the time through the option the surfaces use, and then ends a five-hour-old sign-in at once, red on today's code. Beside it, an agreement test: at a restore, `start()` ends the session at once exactly when `insideSessionCap` says the sign-in is outside.

### 12.3 The idle clock across a relaunch: a launch is activity

The idle limit measures how long an open window has gone untouched. A launch is the person opening WILSON, as a reload or a reopened tab is on the web, where `start()` already writes the idle clock at every start; it keeps doing so at every desktop launch, unchanged, and no idle clock is carried across a relaunch (§12.5 leaves it out of the kept file). What bounds a saved sign-in across launches is the cap (§12.2). An idle sign-out clears the stored session before any network call (App's `signOutLocal`), so a relaunch after one normally finds no saved sign-in; when that clear fails (`clearSession` does not read `wilson:session-clear`'s `unlink_failed`) or the app dies before it lands, the relaunch resumes the session with a fresh idle clock, inside the cap. A window left open signs out at thirty minutes by the wall clock, but when the first thing after a long sleep is a key or a pointer, before any tick or visibility change, `activity()` counts it before anything has judged the absence (round 1, F11): existing behaviour and not this fix's rule to change, recorded in OUTSTANDING with its measurement.

### 12.4 The settings: three ways to keep the renderer's storage, and their costs

**(a) A remembered per-install port.** The first launch keeps the port `listen(0)` gave it; later launches ask for it again and take a new one when it is held. The window loads only the port its own `listen` returned, so a squatter is never the window; but a squatter, another program or a Windows reservation holding the port sends that launch to a new origin with empty storage (the reset this fixes, at random), and Hyper-V and WSL2 reserve blocks of ports that can move at each boot (this machine reserves none in the range; not measured elsewhere). It turns a per-launch location into a fixed one: DNS rebinding from a page in her ordinary browser can aim at it without scanning. The token still refuses every `/api` request (that browser holds neither the cookie nor the header, and the local server checks no Host), and the unguarded static shell answers, as it would at today's port once found. TPN's finding on a fixed port (*it belongs to whoever claims it first*) applies in its mild form: a claim denies the storage, never the content. `localDemoBoundary.test.js` H1 (the literal `listen(0, '127.0.0.1'` line) moves.

**(b) A privileged custom scheme** (`protocol.registerSchemesAsPrivileged` and `protocol.handle`, the window at `wilson://app/`). The origin is fixed and unreachable from any page in her browser. Every renderer request to the local server becomes the handler's to carry: the relative `/api/...` fetches (JSON, the streamed PUT uploads, the downloads), the `<img>` thumbnail routes and the `<video>` Range requests, each forwarded by the main process to `http://127.0.0.1:<port>` with the token, since a cookie set for the loopback origin does not ride a `wilson://` request; `localMediaUrl` and `isLocalServerUrl` reason from `location.origin`. (The recovery email does not move: it links to the project's site, `{{ .SiteURL }}` in `supabase/templates/recovery.html`, never to the window's address.) It is the better architecture and the largest change: a second network path that the whole local API passes through, built in one night before 1.0.

**(c) The renderer's storage kept in a file in userData.** The preload asks the main process synchronously for the kept keys and, at the launch's first load, makes `localStorage` exactly those keys before the page's first script (the spike, §12.1); it reads the page's storage once a second, when the window is hidden and at `pagehide`, and sends what changed; the main process keeps the file. Its costs: a crash loses what changed in its last second (§12.7); two new IPC channels; a file in userData holding what Chromium's own `Local Storage` folder holds today, in the same folder with the same protection; and each launch's origin still starts empty and is then filled, so once the server has bound the main process clears every other origin's `localStorage` (`session.clearData({ dataTypes: ['localStorage'], excludeOrigins: [this launch's origin] })`, not awaited, its failure caught: it never stands between the launch and its first paint and cannot touch the live origin; round 1, F3). Without that clear Chromium keeps one copy per launch on disk for ever; a recycled port cannot bring an old launch's keys back in any case, because the first load clears the origin before it fills it. Nothing moves on the local server, the origin, the token or the cookie: H1 stands, and so does every finding on the loopback bind.
